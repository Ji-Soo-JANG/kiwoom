# 기본 설계서

최종 수정일: 2026-08-29
문서 상태: 초안 기준선 v0.1

## 1. 설계 목표

연구 코드와 실전 주문 코드를 분리하면서 동일한 전략·위험 판단을 PAPER와 LIVE에서 재사용한다. 외부 API나 PC가 불안정해도 중복 주문을 방지하고, 브로커 계좌를 최종 원장으로 삼아 안전하게 복구한다.

## 2. 전체 구조

```text
React UI
  └─ Spring REST API
       ├─ 운영 제어 / 준비 검사 / 감사
       ├─ 전략·신호 엔진 ── 백테스트·평가
       ├─ 위험 엔진
       ├─ 주문·포지션 엔진(OMS)
       │    └─ BrokerAdapter
       │         ├─ PaperBrokerAdapter
       │         └─ KiwoomLiveBrokerAdapter (목표 구현)
       ├─ 시장 데이터·품질·거래일 서비스
       └─ PostgreSQL
            ├─ 시장 데이터와 전략 스냅샷
            ├─ 주문·체결·포지션과 성과
            └─ 운영·대사·감사 기록
```

## 4. 운영 모드와 상태

목표 운영 상태는 다음과 같다.

```text
OFF
 ├─> SIGNAL_ONLY
 ├─> PAPER_RUNNING
 └─> LIVE_ARMED ── 준비 검사/확인 ──> LIVE_RUNNING
                         │                   │
                         └──── 실패 ─────────┴─> HALTED
HALTED ── 원인 해소 + 수동 확인 ──> OFF 또는 이전 허용 모드
```

- `OFF`: 자동 판단과 신규 주문을 수행하지 않는다.
- `SIGNAL_ONLY`: 데이터와 후보만 생성한다.
- `PAPER_RUNNING`: 외부 주문 없이 동일 전략·위험 흐름을 검증한다.
- `LIVE_ARMED`: 실전 선택은 됐지만 주문 전 준비 검사와 확인이 남았다.
- `LIVE_RUNNING`: 실계좌 자동 주문을 허용한다.
- `HALTED`: 신규 매수를 금지한다. 위험 감소 매도는 별도 안전 경로로 처리한다.

현재 구현의 `SIGNAL_ONLY/PAPER/LIVE`와 자동매매 제어는 이 목표 상태 모델로 점진적으로 이전한다.

## 5. 주요 처리 흐름

### 장 전

1. 서버와 DB를 시작한다.
2. 키움 인증·계좌·시장 상태를 확인한다.
3. 최신 거래일 종목 마스터와 일봉을 수집한다.
4. 데이터 품질과 신선도를 검사한다.
5. 전일 미체결, 체결과 보유 포지션을 브로커 원장과 대사한다.
6. 선택 전략 버전과 위험 한도를 고정한 실행 스냅샷을 만든다.
7. 후보를 스캔하고 주문 가능 준비 상태를 결정한다.

### 장중

1. 후보의 최신 가격과 거래 가능 상태를 확인한다.
2. 진입 조건을 다시 평가한다.
3. 위험 엔진이 주문 수량과 허용 여부를 결정한다.
4. 의사결정 ID를 생성해 주문을 한 번만 전송한다.
5. 체결·부분 체결·미체결을 추적하고 포지션을 갱신한다.
6. 기존 포지션의 손절·전략 이탈·익절 조건을 계속 감시한다.
7. API·데이터·대사 이상 시 신규 매수를 중단한다.

### 장 후

1. 미체결과 체결을 최종 조회한다.
2. 계좌 잔고와 로컬 포지션을 대사한다.
3. 거래 비용, 실현·미실현 손익과 일별 위험 지표를 저장한다.
4. 전략 신호 대비 실행 차이와 오류를 기록한다.
5. 다음 거래일에 복구할 상태를 영속화한 뒤 종료 가능 여부를 표시한다.

### 재시작 복구

서버는 로컬 주문을 즉시 재전송하지 않는다. 먼저 브로커의 미체결·당일 주문·체결·잔고를 조회하고, 브로커 주문 ID와 의사결정 ID를 연결한 뒤 불일치를 분류한다. 모호한 상태가 남으면 `HALTED`로 두고 신규 매수를 막는다.

## 6. 데이터 원칙

- 브로커 계좌·주문·체결은 실전 운전의 최종 원장이다.
- DB 일봉은 전략 판정의 재현 가능한 입력 원장이다.
- 신호에는 전략 버전, 데이터 기준일, 특징값, 구간 날짜와 거절 사유를 함께 저장한다.
- 수정주가와 원본 수집 사실을 구분해 기업행사 영향을 추적한다.
- 주문·체결·운영자 조작 기록은 수정 대신 후속 이벤트를 추가한다.

## 7. 안전 설계

- 신규 매수는 모든 준비 검사에 성공해야만 허용한다.
- LIVE 시작은 단순 토글이 아니라 모드 선택, 위험 한도 확인, 계좌 확인과 명시적 재확인을 요구한다.
- 주문 크기는 전략 점수만으로 확대하지 않고 독립 위험 한도의 작은 값으로 제한한다.
- 네트워크 타임아웃은 주문 실패로 단정하지 않고 주문 조회 후 판단한다.
- 전략 오류와 브로커 오류를 분리해 포지션 보호 경로가 가능한 한 유지되게 한다.

## 8. 배포·운영 환경

공개 서비스로 배포하지 않고 사용자 로컬 PC에서 운용한다. Windows 작업 스케줄러가 거래일 기동·종료를 담당할 수 있으나 휴장일 판정은 애플리케이션의 공식 거래일 데이터가 책임진다. PostgreSQL 데이터는 정기 백업하고 API 비밀값은 Git과 DB 일반 설정 테이블에 저장하지 않는다.

## 9. 단계별 완성 기준

| 단계 | 목적 | 다음 단계 진입 조건 |
|---|---|---|
| 연구 | 동적 패턴의 유효성 확인 | 데이터 누수·생존편향 방지, 여러 기간 비용 후 성과 확인 |
| PAPER | 시스템 결정과 상태 흐름 검증 | 충분한 거래일, 신호·체결·청산·복구 안정성 확인 |
| 모의투자 | 실제 API 계약 검증 | 주문 상태·호출 제한·장애 대사 시나리오 통과 |
| 제한 실전 | 소액으로 실제 실행 차이 측정 | 사전 한도 내 안정적 대사와 허용 성과 확인 |
| 실전 자동 | 통제된 자동 운전 | 상시 모니터링·킬 스위치·복구 절차 유지 |
