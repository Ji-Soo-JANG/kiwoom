# PM 프로젝트 현황 종합 검토

- 문서 ID: `PM-REVIEW-001`
- 기준일: 2026-08-29
- 상태: 부서 자료 취합 완료 / 사용자 승인 안건 작성 전
- 입력 자료: `docs/departments/`의 9개 부서 보고서와 프로젝트 구성 지도

## 1. PM 결론

프로젝트는 종목·일봉 저장, 품질 검사, 전략 버전·스캔, 백테스트, PAPER 주문·위험·성과, 자동 스케줄과 React 화면까지 폭넓은 기반을 갖췄다. 자동 테스트와 DB 이력도 개인 프로젝트 수준을 넘어선다.

그러나 현재 구조는 **연구 및 로컬 PAPER 검증 시스템**이다. 실전 자동매매의 수익성과 안전성을 입증하지 않았으며 실제 키움 주문 어댑터, 브로커 원장 대사, 실시간 자산 위험, 준비 검사, 안전 종료와 운영 보안이 없다. LIVE 기능 개발보다 먼저 연구 결과의 신뢰성과 데이터 계보를 바로잡아야 한다.

## 2. 전 부서 공통 합의

다음 판단에는 부서 간 이견이 없다.

1. DB 기반 일봉·품질 검사·시점 유니버스·전략 스냅샷은 유지·강화한다.
2. PAPER 주문 상태 머신·멱등 키·킬 스위치는 좋은 기반이지만 실전 원장으로 간주하지 않는다.
3. 고정 60~1,200일 박스권 비교는 `STR-002`의 동적 안정 구간 요구를 충족하지 않는다.
4. 패턴 후보와 실제 주문 가능한 진입 계획을 분리해야 한다.
5. 주문 크기는 전략 점수가 아니라 무효화 가격과 개인 손실 예산으로 제한해야 한다.
6. 실제 계좌·주문·체결·포지션은 브로커를 최종 원장으로 삼아야 한다.
7. 데이터·브로커·대사 상태가 불확실하면 신규 매수는 실패 폐쇄해야 한다.
8. 기존 수동 포트폴리오 백엔드는 사용자 데이터 보호를 위해 격리하고 계좌 원장으로 사용하지 않는다.
9. 보조 기능인 일반 검색·비교·관심종목·알림은 삭제하지 않되 핵심 자동매매보다 우선순위를 낮춘다.
10. AI는 충분한 데이터와 검증 전에는 분석·제안만 하며 실전 규칙을 직접 변경하지 않는다.

## 3. 즉시 신뢰 차단이 필요한 발견

### PM-BLOCK-001: 백테스트 전략 버전 불일치

`EventBacktestEngine`은 `StrategyPatternDetector`를 직접 생성해 레거시 신호를 계산한다. 하지만 결과의 `strategyVersion`에는 운영 기본 전략인 v3이 기록된다. `BacktestService`도 전략 레지스트리를 주입하지 않는다.

영향:

- 기존 백테스트·워크포워드 결과가 표시된 전략을 실제로 검증하지 않았다.
- 전략 변경 후에도 백테스트가 다른 탐지기를 계속 사용할 수 있다.
- 결과와 코드·파라미터의 감사 추적이 성립하지 않는다.
- 해당 결과를 전략 승격이나 실전 가능성 판단에 사용할 수 없다.

PM 조치 의견:

- 기존 결과는 삭제하지 않는다.
- 사용자 승인 전까지 `참고용/신뢰 미확정`으로 취급한다.
- 운영과 연구가 동일한 `StockStrategy`, 버전, 파라미터를 사용하도록 수정하는 안건을 첫 승인 후보로 올린다.
- 수정 후 기존 결과를 재계산하고 이전 결과와 구분한다.

### PM-BLOCK-002: PAPER 위험 수치가 실제 손실을 반영하지 않음

현재 PAPER 자산 평가는 포지션의 평균 체결가 중심이어서 최신 가격 하락, 미체결 예약 위험과 갭 위험을 충분히 반영하지 않는다. 일 손실·낙폭 킬 스위치가 존재하더라도 실전 수준 손실 통제라고 볼 수 없다.

### PM-BLOCK-003: 실전 주문·대사·복구 부재

현재 브로커 계약은 실제 주문 조회·정정·취소·체결·잔고 수렴을 제공하지 않는다. 주문 타임아웃과 서버 재시작 시 브로커를 먼저 조회하는 절차도 없다. LIVE는 계속 차단되어야 한다.

### PM-BLOCK-004: 안전한 운영 시작·종료 부재

장 전 준비 검사 결과를 원장으로 남기지 않으며 종료 스크립트는 장 후 상태와 무관하게 프로세스를 강제 종료한다. 미체결·대사 오류·백업 완료를 확인하는 종료 게이트가 필요하다.

### PM-BLOCK-005: 실전 보안 통제 부족

CSRF가 비활성화되어 있고 `.env` 평문 비밀, 단일 인메모리 관리자, 운영자 조작 감사 부재, TLS/Secure 쿠키 정책 미확정 상태다. 로컬 개인 사용이어도 실제 주문 권한을 연결하기 전 보강해야 한다.

## 4. 부서 간 의존 관계

```text
데이터 계보·품질·시장 상태
  └─> 동적 전략·구조화된 신호
        └─> 동일 전략 백테스트·검증
              └─> 전략 승격 상태
                    └─> 진입·청산 계획
                          └─> 손실 예산·위험 승인
                                └─> OMS·브로커 대사
                                      └─> 운영 상태·UI·LIVE
```

선행 산출물이 확정되지 않은 상태에서 후행 부서가 임의 계약을 만들면 재작업과 안전 위험이 커진다.

## 5. PM 권고 작업 묶음

아래는 아직 승인되지 않은 제안이다. 구현 전에 각 묶음별 상세 제안서와 사용자 승인이 필요하다.

### 묶음 A — 연구 신뢰성 복구(P0)

- 운영·백테스트·워크포워드의 전략 계약과 버전 통일
- 기존 결과에 신뢰 상태를 부여하고 승격 입력에서 격리
- 전략 코드 해시·파라미터·데이터 기준 연결
- 요구사항과 테스트 추적표 작성

관련 제안: `STR-P03`, `RES-P01`, `RES-P02`.

### 묶음 B — 데이터 계보와 동적 전략 기반(P0)

- 수집 실행·조정 정책·품질 실행·전략 실행 계보 연결
- 전략 필요 이력과 종목 후보 하한 통일
- 동적 안정 구간 연구와 골든 사례·반례 데이터셋
- 네 구간 날짜·게이트·거절 코드 구조화

관련 제안: `DAT-P01`, `DAT-P02`, `STR-P01`, `STR-P02`, `QA-001`.

### 묶음 C — 진입·청산·자금 위험(P0)

- 신호와 진입 계획 분리
- 최대 진입가, 무효화 가격, 예상 손실과 청산 계획
- 최신 시가평가·미체결 예약을 반영한 개인 손실 예산
- 시장·업종·거래 가능 상태 게이트

관련 요구사항: `CAP`, `ENT`, `EXT`, `MKT`.

### 묶음 D — 브로커 중립 주문·복구(P0)

- BrokerAdapter v2 계약
- 모호한 주문 상태와 브로커 주문 ID 매핑
- 주문·체결·잔고·포지션 대사
- 재시작 복구와 보호 매도
- 키움 모의투자 현장 계약 검증

관련 제안: `QA-003`, `QA-004`, `QA-006` 및 매매시스템팀 제안.

### 묶음 E — 운영·보안·UI(P0/P1)

- 장 전 readiness와 단계별 실행 원장
- 안전 종료, 백업·복원, 공식 거래일
- 비밀 저장, 인증·CSRF·감사 통제
- 모든 화면의 운전 상태 막대와 주문·대사 상태

관련 요구사항: `OPS`, `NFR`, `UI`.

## 6. 보존·격리·수정 분류

| 분류 | 대상 |
|---|---|
| 유지·강화 | 시장 데이터 DB, 품질 이력, 시점 유니버스, 전략 레지스트리, 스냅샷, 이벤트형 연구 기반, PAPER 주문 이벤트·멱등성, 테스트·CI |
| 격리 | 레거시 전략, 기존 불일치 백테스트 결과, 수동 포트폴리오 백엔드, 제한 매매의 임시 고정값 |
| 우선순위 하향 | 일반 비교, 관심종목 꾸미기, 일반 알림, 시장 카드 개인화 |
| 구조 수정 | 전략/검증 계약, 데이터 계보, DTO·서비스 도메인 경계, 브로커 계약, 위험 평가, 스케줄 원장, 자동매매 UI |
| 당장 제거 금지 | 기존 DB 테이블·사용자 데이터·과거 연구 결과·PAPER 회귀 도구 |

## 7. 부서 간 조율이 필요한 쟁점

| 쟁점 | 관련 부서 | PM 조정 방향 |
|---|---|---|
| 안정 구간 최소 기간 | 전략·데이터·QA | 기간은 사업 자격 조건으로 두지 않고 통계 계산 최소 표본만 정한다. |
| 최대 보유기간 | 전략·위험·매매 | 핵심 패턴 규칙과 자금 회수 안전 규칙을 분리해 검증한다. |
| 시장 위험 상태 | 데이터·전략·위험 | 원천을 먼저 확정하고 `UNKNOWN`은 신규 매수 차단으로 둔다. |
| LIVE 시작 확인 주기 | 위험·운영·UI | 거래일 단위 준비 검사와 중요한 설정 변경 시 재확인을 우선 검토한다. |
| 기존 결과 처리 | 전략·성과검증·데이터 | 삭제 없이 신뢰 상태를 부여하고 재계산 결과와 분리한다. |
| 레거시 포트폴리오 | 백엔드·데이터·UI | 읽기·내보내기만 보존하고 자동매매 원장에서 제외한다. |

## 8. 사용자 결정이 필요한 항목

아직 수치나 구현 방식을 임의로 확정하지 않는다.

- 개인 초기 운용 원금과 단계별 증액 한도
- 거래당·일간·월간 허용 손실과 최대 낙폭
- 최대 동시 보유, 종목·업종·총노출 한도
- 전략 승격에 필요한 최소 기간·표본·허용 낙폭
- 동적 안정 구간 알고리즘 연구 범위
- 시장·기업행사·과거 유니버스 외부 데이터 원천과 비용 허용 여부
- 지정가·시장가, 미체결 만료·재가격과 갭 청산 정책
- 실전 인증·비밀 저장과 운영 알림 방식
