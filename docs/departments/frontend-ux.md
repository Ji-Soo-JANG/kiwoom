# 프론트엔드·UX팀 프로젝트 현황 조사서

- 문서 상태: 부서 조사 초안
- 조사 기준일: 2026-08-29
- 담당 부서: 프론트엔드·UX팀
- 검토 대상 요구사항: `UI-001~004`, `NFR-005`, `NFR-008` 및 관련 `STR`, `TRD`, `RSK`, `OPS`
- 작성 범위: 현재 React 구현을 조사한 결과와 목표 UI의 차이를 기록한다.

## 1. 부서 결론

현재 화면은 종목 검색·차트·발견·계좌·PAPER 자동매매 상태를 한 애플리케이션에서 확인할 수 있고, React Query와 공통 비동기 상태를 사용해 기본 사용성은 확보되어 있다. 전략 후보를 클릭해 차트로 이동하고 실제 키움 계좌 포트폴리오를 표시하는 흐름도 목표와 맞는다.

반면 전체 정보 구조의 중심이 아직 “주가 조회”이며, 실전 자동매매 운영자에게 가장 중요한 운전 모드, 실주문 가능 여부, 데이터 신선도, 브로커·대사 상태와 손실 예산이 전역에서 보이지 않는다. 자동매매 화면은 PAPER 검증 정보를 한 페이지에 밀집시켰고 LIVE 요청 토글은 실제 주문 능력이 없는 상태라 오해 방지가 최우선이다.

## 3. 프론트엔드 구조와 흐름

- React 19, React Router, TanStack Query, Recharts, Vite를 사용한다.
- `AuthGate`가 `/api/auth/me`로 세션을 확인하고 401이면 정적 로그인 화면으로 이동한다.
- `kiwoomApi.js`가 쿠키 포함 요청, 오류 응답 변환과 모든 API 함수를 한곳에서 제공한다.
- `App.jsx`가 라우팅뿐 아니라 종목 검색 상태, 관심종목 변경과 비교 목록까지 관리한다.
- 차트는 지연 로딩하고 Recharts를 별도 번들로 분리한다.
- 시장 발견 카드 순서·표시 개수·시장은 `localStorage`에 저장한다.
- 프론트 빌드 결과는 Spring Boot의 `src/main/resources/static`에 생성되어 8080 단일 서버에서도 제공된다.

## 4. 요구사항별 구현 판정

| 요구사항 | 현재 판정 | 차이 |
|---|---|---|
| `UI-001` | 미흡 | 자동매매 화면 설명에는 LIVE 차단이 있으나 모든 화면에 모드·실주문 가능·자동운전·시장 상태가 표시되지 않음 |
| `UI-002` | 부분 구현 | 전략 후보, 점수, 급락·박스·눌림 지표와 클릭 이동은 있다. 동적 구간 날짜·차트 오버레이·탈락 근거가 부족 |
| `UI-003` | 부분 구현 | PAPER/LIVE 토글과 전략 선택은 있다. readiness, 손실 예산, 실전 단계 승인, 강한 확인 절차가 없음 |
| `UI-004` | 부분 구현 | 키움 계좌 평가잔고는 표시하나 미체결, 브로커 갱신 시각, 대사 상태와 실현·미실현 상세 연결이 부족 |
| `NFR-005` | 부분 구현 | 한국어 상태와 빈 화면 컴포넌트는 좋지만 자동매매 화면 정보량과 전문 용어가 많음 |
| `NFR-008` | 부분 구현 | 후보 조건·전략 파라미터는 보이나 진입·차단·청산 판단 당시 입력값과 우선 사유가 충분하지 않음 |

## 5. 강점과 유지 대상

- 검색 탭과 차트 탭이 분리되어 탐색 흐름이 명확하다.
- 후보·순위 클릭이 종목 차트로 이어져 추가 입력을 줄인다.
- 실제 키움 계좌 API를 포트폴리오의 출처로 사용한다.
- 로딩·오류·빈 상태 컴포넌트, `role`, `aria-label`, 키보드 버튼 등 접근성 기반이 있다.
- React Query가 서버 상태 캐시와 갱신을 담당하여 비동기 상태 중복을 줄인다.
- API 오류 코드를 사용자가 이해할 한국어 문장으로 변환한다.
- 단위 테스트, 접근성 E2E, 번들 크기 예산과 OpenAPI 타입 사용 검사가 빌드에 포함된다.

## 6. 문제와 개선 필요 항목

### P0: 운영 안전 UX

1. 페이지 상단에 항상 보이는 운영 상태 막대가 필요하다: `신호/PAPER/모의/LIVE`, 실제 주문 가능 여부, 자동운전 ON/OFF, 시장 상태, 마지막 대사, 킬 스위치.
2. 현재 LIVE 토글은 실제 제출 불가 상태에서도 켤 수 있다. 목표 상태에서는 준비 검사와 실전 승격을 통과하기 전 비활성화하고 이유를 항목별로 보여줘야 한다.
3. 위험 한도와 예상 손실을 단순 설정값이 아니라 현재 사용량과 함께 표시해야 한다.
4. 주문·포지션 화면은 브로커 원장 갱신 시각과 불일치 여부를 항상 노출해야 한다.
5. 위험한 조작은 색상만으로 구분하지 않고 대상 계좌·전략·한도·결과를 문장으로 재확인해야 한다.

### P1: 정보 구조와 설명 가능성

1. `LimitedTradingPanel`은 제어, 전략 카탈로그, 관찰, 후보, 보유, 청산, 결과, 성과를 한 컴포넌트에 담는다. 운영 대시보드·자동매매 설정·주문/포지션·성과 화면으로 분리할 필요가 있다.
2. `App.jsx`가 라우터와 검색·관심종목·비교의 업무 상태를 함께 가진다. 기능별 페이지 컨테이너로 이동해야 한다.
3. 종목 발견 화면의 `BASE_WINDOWS=[60,120,240,480,720,1200]`과 `boxRangeDays` 선택은 `STR-002` 목표와 충돌한다. 동적 탐지에서는 기간을 입력 조건이 아니라 검출 결과로 표시해야 한다.
4. 후보 상세에는 급락 시작·종료, 안정 구간, 거래량 사건, 회복 고점, 현재 눌림을 차트 위에 표시해야 한다.
5. `kiwoomApi.js`가 모든 도메인의 요청을 포함한다. 인증·시장·전략·거래·운영 API 모듈로 분리하되 공통 오류 계약은 유지한다.

### P2: 유지·격리 판단

- 종목 검색과 관심종목은 연구·수동 확인에 유용하므로 제거하지 않는다.
- 비교·일반 알림·카드 사용자 설정은 자동매매 핵심 화면과 분리하고 개발 우선순위를 낮춘다.
- 수동 포트폴리오 화면은 이미 제거됐으며 계좌 기반 `AccountPortfolio`를 유지한다.
- `public/login.html`과 Spring 정적 `login.html`의 생성·복사 책임을 명확히 하여 중복 수정 위험을 줄인다.

## 7. 목표 화면 제안

```text
공통 운영 상태 막대
├─ 운영 대시보드: 오늘 준비 검사, 후보, 주문, 손익, 경고
├─ 종목 발견: 전략별 현재 후보와 판정 근거
├─ 종목 상세: 가격·거래량·패턴 구간·진입/무효화 계획
├─ 자동매매: 전략 승격, PAPER/LIVE, 위험 정책, ON/OFF
├─ 주문·포지션: 브로커 원장, 미체결, 청산 계획, 대사 상태
├─ 성과: 전략 버전·시장 국면·비용 후 성과
└─ 운영 상태: 데이터, 키움, 스케줄, 실행 이력, 오류 조치
```

화면에는 다음 공통 상태가 필요하다.

- 로딩: 어떤 자료를 불러오는 중인지 표시
- 빈 상태: 정상적인 0건과 준비 미완료를 구분
- 경고: 주문에는 영향 없지만 확인이 필요한 상태
- 차단: 신규 매수가 중단된 이유와 해결 순서
- 불확실: 응답 타임아웃처럼 결과 확인 전 재시도하면 안 되는 상태
- 오래된 자료: 마지막 갱신 시각과 자동 갱신 여부 표시

## 10. 미결정 쟁점

- 실전 운전 시작 시 매회 확인할지, PC·거래일 단위로 승인할지
- 위험 수치 변경을 즉시 반영할지 다음 운전일부터 반영할지
- 동적 패턴 구간이 겹칠 때 차트와 목록에 보여줄 대표 패턴 선택법
- 계좌번호·주문번호·손익 자료의 마스킹 수준
- 모바일 대응 범위와 최소 화면 크기
- 운영 경고를 화면 내 알림만 사용할지 별도 외부 알림과 연결할지
