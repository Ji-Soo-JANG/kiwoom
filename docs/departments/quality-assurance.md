# QA·검증팀 프로젝트 현황 조사서

- 문서 상태: 부서 조사 초안
- 조사 기준일: 2026-08-29
- 담당 부서: QA·검증팀
- 검토 대상 요구사항: 전체 요구사항, 특히 `RES`, `PRM`, `TRD`, `RSK`, `OPS`, `NFR-003`, `NFR-006`
- 작성 범위: 자동 테스트, 픽스처, CI와 기존 검증 문서를 기준으로 조사한다.

## 1. 부서 결론

현재 프로젝트는 백엔드 단위·저장소·계약 테스트와 프론트 단위·접근성 E2E, 정적 분석, 커버리지 게이트를 갖추고 있어 개인 프로젝트 수준을 넘어선 검증 기반이 있다. 전략 시간 순서, 워크포워드, 부분 체결·취소·복구 같은 자동매매 특화 테스트가 존재하는 점도 강점이다.

하지만 현재 테스트 통과는 PAPER 로컬 원장이 예상대로 동작한다는 의미이지 실전 주문 안전성을 증명하지 않는다. 실제 키움 모의·실전 계약, 호출 제한, 장 운영 이벤트, 재시작 후 브로커 원장 대사, 손실 한도와 보호 매도에 대한 현장 검증이 빠져 있다. 커버리지 수치만으로 LIVE 승격을 허용해서는 안 된다.

## 2. 현재 검증 체계

### 2.1 백엔드

- JUnit/Spring Boot Test, Mockito, MockWebServer, Spring Security Test 사용
- 코드상 `@Test` 약 149개
- JaCoCo `verify` 게이트:
  - instruction 80%
  - branch 60%
  - line 80%
  - method 75%
- Spotless가 Maven `validate`에 연결됨
- `kiwoom-live` Maven 프로필에서 `*IT.java` 실연동 시험을 별도로 실행
- H2 R2DBC와 테스트 스키마, 키움 응답 JSON 픽스처 사용

주요 시험 영역:

- 키움 HTTP 인증·재시도·페이징·응답 매핑
- 시장 데이터 수집·품질·거래일
- 전략 탐지·레지스트리·스캔 파이프라인
- 이벤트 백테스트·워크포워드
- 주문 상태 머신, 부분 체결, 취소, 중복 방지
- PAPER 위험, 스윙 감시, 업무 스케줄
- 저장소 통합과 OpenAPI 계약

### 2.2 프론트엔드

- Vitest, Testing Library, jsdom 사용
- 코드상 `describe/test/it` 약 89개
- V8 커버리지 게이트:
  - statements 70%
  - branches 65%
  - functions 55%
  - lines 74%
- ESLint, Prettier, TypeScript 기반 OpenAPI 타입 사용 검사
- Playwright Chromium E2E와 axe 접근성 검사
- 빌드 산출물 변경 검사와 번들 크기 예산 검사

### 2.3 CI

`main` push와 pull request에서 다음을 실행한다.

1. 백엔드 `clean verify`와 JaCoCo 보고서 업로드
2. 프론트 `npm ci`, 보안 감사, 포맷, 린트
3. OpenAPI 타입 생성 차이와 타입 사용 검사
4. 단위 테스트와 커버리지
5. Chromium E2E
6. 프론트 빌드 산출물 일치와 번들 크기 검사

## 4. 강점과 유지 대상

- 백엔드와 프론트 모두 커버리지 하한이 CI에서 강제된다.
- OpenAPI 문서와 생성 타입의 차이를 CI가 감지한다.
- 실제 외부 API와 독립된 JSON 픽스처가 결정론적 회귀 시험을 가능하게 한다.
- 주문 승인·거부·타임아웃·부분 체결·정정·취소 픽스처가 있다.
- 전략 단위뿐 아니라 스캔 파이프라인과 스케줄러도 시험한다.
- Playwright E2E에 접근성 자동 검사가 포함되어 있다.
- 실 API 시험을 기본 테스트에서 분리해 비밀정보와 외부 장애의 영향을 줄인다.

## 5. 검증 공백과 위험

### P0: LIVE 차단 조건

다음 시험의 근거가 없으면 실전 승격을 승인하지 않는다.

1. 같은 주문 의사결정이 재시도·프로세스 재기동·응답 유실 후에도 한 번만 제출된다.
2. 타임아웃 주문은 브로커 조회 전 재주문되지 않는다.
3. 부분 체결, 정정·취소 경쟁 상태와 장 마감 미체결이 브로커 원장에 수렴한다.
4. 로컬 주문·현금·수량 불일치 시 신규 매수가 자동 차단된다.
5. 매수 차단 중에도 검증된 보호 매도가 보유 수량을 초과하지 않고 동작한다.
6. 데이터 누락·지연, 인증 만료, 호출 제한, 네트워크 단절, 키움 5xx를 주입했을 때 실패 폐쇄된다.
7. 킬 스위치와 손실 한도가 재시작 후에도 유지된다.
8. 실제 키움 모의투자에서 주문·체결·잔고 필드와 호출 제한이 픽스처와 일치한다.

### P1: 테스트 구조 부채

1. H2 테스트와 PostgreSQL 실제 동작 차이를 포착할 Testcontainers 기반 통합 시험이 없다.
2. E2E는 프론트 개발 서버만 시작하므로 실제 Spring Security·세션·DB·API 통합을 검증하지 않는다. API 모킹 범위도 명문화해야 한다.
3. 전체 테스트 개수는 많지만 요구사항 ID와 테스트 케이스의 추적표가 없다.
4. 전략 테스트가 특정 예제에 과적합될 위험이 있다. 생성형·속성 기반 테스트와 고정 골든 데이터셋이 필요하다.
5. 스케줄러의 시간대, 휴장, 중복 실행과 프로세스 종료 중 동작을 시스템 수준에서 검증하지 않는다.
6. OpenAPI 계약은 검사하지만 이전 버전과의 호환성 정책은 없다.
7. 성능·부하·장 전 전체 종목 스캔 완료 시간에 대한 기준과 측정이 없다.

### P2: 운영 품질

- 테스트 보고서가 커버리지 중심이며 전략 성능, 대사 오류율, 주문 지연과 데이터 품질 추세를 한 결과로 묶지 않는다.
- 실패 픽스처에 버전·출처·마스킹·재현 조건 메타데이터가 부족하다.
- 사용자 로컬 Windows 환경의 실제 기동·종료·Docker PostgreSQL 복원 검증을 자동화할 필요가 있다.

## 6. 제안하는 검증 단계와 승격 게이트

| 단계 | 필수 검증 | 통과 결과 |
|---|---|---|
| 코드 | 단위·계약·정적 분석·커버리지 | 병합 가능 |
| 통합 | PostgreSQL, Spring Security, API, 스케줄 전체 흐름 | 로컬 PAPER 가능 |
| 연구 | 미래 데이터 누수, 외부 표본, 비용, 강건성 | 전략 관찰 가능 |
| PAPER | 신호·체결 모델·청산·성과·운영 오류율 | 모의투자 후보 |
| 키움 모의 | 실제 주문 계약, 속도 제한, 부분 체결, 재시작 대사 | 최소 실전 후보 |
| 장애 훈련 | 인증·네트워크·데이터·DB·프로세스 장애와 킬 스위치 | 제한 실전 후보 |
| 최소 실전 | 최소 금액·종목, 일별 대사, 계획 대비 체결 | 제한 실전 검토 |
| 제한 실전 | 승인된 기간과 한도 내 안정성 | 정상 실전 승인 요청 |

승격은 승률 하나가 아니라 비용 후 기대값, 최대 낙폭, 표본 수, 주문·대사 오류율, 계획 대비 슬리피지와 운영 장애 횟수를 함께 본다(`PRM-001~003`).

## 9. 미결정 쟁점

- LIVE 전 PAPER·모의투자 최소 거래일·표본 수
- 전략별 허용 최대 낙폭과 성능 저하 탐지 기준
- 키움 모의투자와 실전 환경 차이를 보완할 최소 실전 시험 범위
- 네트워크 장애 시험을 실제 장중에 수행할 수 있는 안전 범위
- 거래 비용·세금·호가 미끄러짐 기준 데이터의 출처와 갱신 주기
- 운영 PC 장애 시 복구 시간 목표와 수동 개입 한계
