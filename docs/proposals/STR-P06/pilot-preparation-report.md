## 1. PM 결론

승인된 범위대로 실제 개발 PostgreSQL의 저장 일봉을 사용해 배치 1을 생성했다. 30종목 모두 평가 후보가 생성됐고 서버가 기준일 이후 봉을 평가 API에서 차단한다. 이 시점은 파일럿 완료나 전략 승격이 아니다. 사용자가 30개를 블라인드로 평가하고, 필요한 반복 평가와 결과 공개를 마친 뒤에야 성과 보고서를 작성한다.

## 3. 블라인드·누수 검증

- 후보 생성은 기준일 이하의 일봉만 사용한다.
- 평가용 캔들 API의 마지막 날짜가 기준일 `2026-07-23`임을 실제 호출로 확인했다.
- 후보 90개의 종료일이 기준일을 초과한 사례는 0건이다.
- 사후 20거래일 데이터는 DB에 존재하지만 평가 확정 전 응답에 포함하지 않는다.
- 결과 공개는 확정된 평가에 대한 명시적 요청 뒤에만 수행한다.

## 4. 사용자 평가 절차

1. PostgreSQL 컨테이너와 백엔드·프론트엔드를 개발 모드로 실행한다.
2. 로그인 후 `박스권 평가` 탭으로 이동한다.
3. 배치 `STR-P06 actual-data pilot v1`을 선택한다.
4. 미래 결과를 열지 않고 후보 경계, 라벨, 확신도, 근거, 메모를 입력해 확정한다.
5. 30개를 먼저 모두 확정한 후 성과 공개를 진행한다.
6. 애매하거나 데이터 이상이 의심되는 항목은 메모에 남기며 임의 삭제하지 않는다.

## 5. 성과 보고에 반드시 포함할 항목

- 그룹·후보 유형별 선택률과 거절률
- 자동 후보 대비 사용자 경계 시작·종료 수정 거리
- 라벨, 확신도, 근거 코드 분포
- 반복 평가 표본의 일치율과 불일치 원인
- 5·10·20거래일 수익률, MFE, MAE, 장벽 선도달 분포
- 성공·실패·애매·데이터 이상 사례의 대표 차트
- 표본 수가 작은 데서 오는 불확실성과 해석 금지 항목
- 알고리즘 변경안, 유지안, 폐기안 및 다음 승인 요청

## 6. 완료 판정 기준

30개 전부의 유효 평가가 확정되고, 계획된 반복 평가와 성과 공개가 끝나며, 위 통계와 사례 검토가 문서화되어야 파일럿을 완료로 바꾼다. 단순히 배치를 생성했거나 수익률이 높게 나온 것만으로 완료·성공·전략 승격이라 표현하지 않는다.

## 7. 확인된 운영 이슈

로컬 DB에 성공 적용된 V25의 Flyway 체크섬(`259085582`)과 현재 Git 커밋본의 체크섬(`-2022783191`)이 다르다. 7개 평가 테이블은 존재하며 배치 생성도 성공했지만, 기본 설정으로 서버를 재기동하면 검증 단계에서 중단된다. 이번 파일럿 준비에서는 DB 이력을 변경하지 않고 `SPRING_FLYWAY_VALIDATE_ON_MIGRATE=false`를 일시 사용했다. 실제 운용 전에 스키마 구조 대조 증적을 남기고 표준 `repair`로 로컬 이력을 정합화하는 별도 유지보수 작업이 필요하다.

## 8. 주문 기능과의 격리

이 배치는 연구 평가 테이블만 변경했다. 실주문, PAPER 주문, 자동매매 ON/OFF, 전략 승격 상태를 변경하지 않았다. API 키·시크릿·계좌 비밀을 문서나 Git에 저장하지 않았다.
