# STR-P06 사용자 박스권 평가 워크벤치 — 전략·데이터 합동 검토서

- 문서 ID: `STR-P06-STR-DAT-01`
- 작성 부서: 전략연구팀, 데이터팀
- 상태: PM 검토 전 제안
- 기준일: 2026-08-29
- 관련 요구사항: `DAT-001`~`DAT-004`, `STR-001`~`STR-005`, `RES-001`, `NFR-002`, `NFR-006`, `NFR-008`
- 구현 여부: 미승인·미구현

## 1. 제안 목적

사용자가 생각하는 “박스권”을 코드 작성자가 하나의 수식으로 먼저 고정하지 않는다. 실제 PostgreSQL 일봉을 기준일 당시 상태로 동결하고, 서로 다른 성격의 박스권 후보를 한 차트에 제시해 사용자가 선택·수정·반려할 수 있는 평가 워크벤치를 먼저 만든다. 그 결과를 향후 동적 안정 구간 알고리즘의 골든 데이터와 검증 근거로 사용한다.

워크벤치는 종목 매수 추천이나 자동 주문 기능이 아니다. 사용자 라벨도 즉시 실전 규칙으로 반영하지 않고, 전략 연구와 평가 데이터로만 보존한다.

## 2. 해결하려는 쟁점

현행 전략은 60·120·240·480·720·1200일 고정 창 중 점수가 가장 높은 구간을 선택한다. 이는 수개월부터 수년까지 길이가 달라질 수 있고 기간 자체는 중요하지 않다는 사용자 정의와 맞지 않는다(`STR-002`). 반대로 동적 알고리즘 하나를 바로 채택하면 다음 정의 차이를 숨긴 채 잘못된 기준을 고착할 위험이 있다.

- 매우 좁고 최근의 안정 구간을 박스권으로 볼 것인가
- 변동폭이 조금 넓어져도 동일 가격 상태가 이어졌다면 하나로 볼 것인가
- 중간의 짧은 이탈·갭·거래량 급증을 허용해 앞뒤 구간을 연결할 것인가
- 급락 직후의 가격 발견 구간을 박스권 시작에 포함할 것인가
- 완만한 기울기나 계단식 저점 상승을 횡보로 인정할 것인가

따라서 알고리즘은 정답 하나가 아니라 근거가 다른 복수 후보를 만들고, 차이는 명시적으로 비교돼야 한다.

## 3. 적용 범위와 비범위

### 포함

- PostgreSQL `daily_candle` 기반 종목·기준일 평가
- 기준일에 이용 가능했던 종목과 일봉만 사용하는 데이터 동결
- 역방향 확장과 변화점 탐지를 혼합한 복수 후보 생성
- 좁은 후보, 확장 후보, 연결 후보의 비교
- 후보별 특징·경계·탈락 근거 표시
- 사용자의 선택, 경계 수정, 라벨과 메모 저장 계약
- 데이터 부족·품질 차단·재현성 상태 표시

### 제외

- 후보를 이용한 자동 주문
- 사용자 라벨을 이용한 자동 학습 또는 전략 자동 변경
- 박스권 정답 알고리즘의 최종 확정
- 장중 시세를 이용한 박스권 판정
- 기존 전략 v3 또는 기존 스캔 결과의 덮어쓰기

| 확장 후보 | 좁은 후보를 과거 방향으로 확장해 동일 상태로 볼 수 있는 최대 구간. |
| 연결 후보 | 짧은 구조적 단절을 허용하고 유사한 앞뒤 안정 상태를 연결한 구간. |
| 사용자 경계 | 자동 후보를 사용자가 수정한 시작일·종료일. 자동 원본 경계는 그대로 보존한다. |

## 5. 전략연구팀 후보 생성 설계

### 5.1 전체 순서

```text
최신 일봉에서 현재 눌림 확인
→ 직전 회복 파동과 회복 시작 앵커 추정
→ 앵커에서 과거 방향으로 엄격한 안정 구간 확장
→ 가격·변동성·기울기 변화점 후보 탐색
→ 역방향 확장 경계와 변화점 경계를 조합
→ 좁은/확장/연결 후보 생성
→ 각 후보 특징과 차이 산출
→ 사용자 평가 대상으로 제시
```

현재 눌림과 회복 앵커를 찾지 못하더라도 “박스권 라벨 수집 모드”에서는 사용자가 차트의 임의 구간을 지정할 수 있다. 다만 이런 표본은 전략 전체 패턴 라벨이 아니라 박스권 단독 라벨로 구분한다.

### 5.2 역방향 확장

앵커 직전의 작은 초기 구간에서 시작하여 한 거래일 또는 작은 묶음 단위로 과거 방향으로 확장한다. 매 확장 단계에서 다음 강건 특징을 다시 계산한다.

- 10·90 분위 가격 대역폭과 중앙가격 대비 비율
- 핵심대역 안 종가 체류율
- Theil–Sen 등 이상치에 덜 민감한 기울기 후보
- 일간 수익률 실현 변동성과 최근 회복 구간 대비 변동성 축소율
- 최대 연속 이탈일과 전체 이탈 비율
- 거래량 중앙값, 급증 횟수·배수·간격
- 거래량 급증일 가격 반응과 일정 기간 뒤 가격 유지율

확장 중 한 번의 위반으로 즉시 끝내지 않는다. 누적 위반 점수와 연속 위반을 구분한다. 짧은 이탈은 연결 후보의 근거가 될 수 있지만 장기간 가격 수준이 달라지는 경우에는 경계로 본다.

### 5.3 변화점 혼합

역방향 확장만 사용하면 임계값 부근에서 경계가 불안정하다. 따라서 다음 시계열의 변화점 후보를 별도로 찾는다.

- 로그 종가 수준 또는 강건 중앙가격
- 일간 수익률 변동성
- 가격 범위와 체류율
- 거래량 기준선

변화점은 하나의 최종 경계가 아니라 경계 후보 목록이다. 역방향 확장 종료점과 가까운 변화점은 경계 신뢰도를 높이고, 서로 멀면 복수 후보를 유지하며 불일치 이유를 표시한다. 알고리즘 종류와 페널티는 평가 파라미터로 버전 관리한다.

### 5.4 세 후보의 생성 규칙

#### 좁은 후보(`NARROW`)

- 앵커에 인접한 구간 중 엄격한 대역폭·체류율·기울기·변동성 조건을 모두 만족한다.
- 구조적 변화점 이후만 포함한다.
- 최근 상태를 가장 잘 설명하지만 장기 축적 기간을 과소평가할 수 있다.

#### 확장 후보(`EXPANDED`)

- 좁은 후보에서 과거 방향으로 확장한다.
- 완화된 대역폭과 소수의 비연속 이탈을 허용하되 중앙가격·변동성 상태가 같은 범주여야 한다.
- 역방향 위반 점수가 한도를 넘거나 강한 변화점을 만나면 종료한다.
- 장기 상태를 포착하지만 서로 다른 가격 상태를 합칠 수 있다.

#### 연결 후보(`CONNECTED`)

- 앞뒤 안정 구간의 중앙가격 대역과 변동성이 유사하고, 그 사이 단절이 허용 길이 이내일 때 생성한다.
- 단절 사유는 거래량 급증, 일시적 돌파 실패, 갭, 데이터 누락, 기업행사 의심 등으로 분리한다.
- 데이터 누락이나 미확인 기업행사는 자동 연결하지 않고 검토 필요 상태로 둔다.
- 축적 중 일시적 흔들림을 포착하지만 사후적으로 편리한 구간만 연결하는 위험이 가장 크다.

후보가 실질적으로 같은 경계를 가지면 중복을 합치되, 어떤 생성기가 같은 결과를 지지했는지 근거 목록에 남긴다. 후보 수는 기본 3개 유형별 상위 1개를 권고하되, 경계 불일치가 큰 경우 유형별 보조 후보를 허용한다. 정확한 최대 개수는 UI 복잡도와 연구 효율을 보고 결정한다.

### 5.5 후보 특징 계약

각 후보는 최소한 다음 정보를 가진다.

| 그룹 | 필드 예시 |
|---|---|
| 식별 | 평가 ID, 후보 ID, 생성 유형, 알고리즘 버전, 파라미터 버전 |
| 경계 | 자동 시작·종료 거래일, 거래일 수, 앵커일, 경계 근거 변화점 |
| 가격 | 중앙가격, 강건 하단·상단, 대역폭, 체류율, 이탈 횟수·최대 연속일 |
| 추세·변동성 | 강건 기울기, 수익률 변동성, 이전 구간 대비 축소율, 변화점 신뢰도 |
| 거래량 | 중앙 거래량, 급증 횟수·배수·간격, 급증일 가격 반응·유지율 |
| 전체 패턴 연결 | 직전 급락 구간, 회복 시작·고점, 회복률, 현재 눌림률과 시간 순서 |
| 품질 | 일봉 수, 누락 예상일, 품질 실행 ID, 차단·경고 코드 |
| 설명 | 통과 게이트, 완화한 게이트, 거절·주의 사유 코드와 사람이 읽는 설명 |

특징의 계산식, 단위, 결측 처리, 반올림 전 원값은 특징 사전으로 버전 관리한다. UI 표시용 반올림값을 연구 원본으로 저장하지 않는다.

### 5.6 초기 평가 파라미터

다음은 확정 규칙이 아니라 워크벤치 후보 다양성을 만들기 위한 실험 파라미터다.

- 최소 통계 표본 수
- 핵심대역 분위수와 최대 대역폭
- 최소 체류율
- 최대 절대 기울기와 변동성 축소율
- 허용 이탈 비율·최대 연속 이탈일
- 거래량 급증 배수와 최소 급증 간격
- 변화점 알고리즘, 페널티와 최소 구간 길이
- 확장 위반 점수와 연결 가능 최대 간격
- 연결 전후 중앙가격·변동성 유사도
- 앵커 추정의 최근성 범위

박스권의 총 일수는 특징으로 기록하되 짧거나 길다는 이유만으로 자격을 정하지 않는다. 단, 통계 계산에 필요한 최소 표본과 저장 데이터 탐색 상한은 기술 조건으로 별도 표시한다.

## 6. 사용자 수정과 라벨 계약

### 6.1 가능한 사용자 행동

- 자동 후보 하나를 `가장 적합`으로 선택
- 후보를 `허용 가능`, `부적합`, `판단 보류`로 평가
- 자동 시작일·종료일을 거래일 단위로 수정
- 자동 후보 없이 새 경계를 직접 지정
- 여러 구간으로 분리해야 한다는 라벨 지정
- 앞뒤 구간을 연결해야 한다는 라벨 지정
- 이탈일 포함/제외 의견과 자유 메모 작성
- 종목 전체 패턴이 아니라 박스권 정의만 평가했음을 표시

### 6.2 라벨 값

| 항목 | 값 |
|---|---|
| 적합성 | `BEST`, `ACCEPTABLE`, `REJECTED`, `UNSURE` |
| 수정 유형 | `UNCHANGED`, `BOUNDARY_EDITED`, `MANUAL_CREATED`, `SPLIT_REQUIRED`, `MERGE_REQUIRED` |
| 거절·수정 사유 | 너무 좁음, 너무 넓음, 추세 구간 포함, 급락 구간 포함, 회복 구간 포함, 이탈 과다, 가격 상태 불일치, 데이터 문제, 기타 |
| 평가 범위 | `BASE_ONLY`, `FULL_PATTERN` |

사용자 경계 수정은 자동 후보를 덮어쓰지 않는다. 평가 당시 자동 후보, 수정 경계, 라벨, 메모, 평가 시각과 라벨 스키마 버전을 함께 보존한다. 이후 라벨 변경은 새 리비전으로 저장하며 최초 의견을 삭제하지 않는다.

### 6.3 학습·검증 사용 제한

- 동일 종목·비슷한 기간의 라벨이 학습과 최종 평가에 동시에 들어가지 않도록 그룹 분할한다.
- 사용자가 이미 본 후보를 알고리즘 최종 성능의 독립 검증 표본으로 재사용하지 않는다.
- 단일 사용자의 주관 라벨은 절대적 정답이 아니라 선호와 전략 정의를 구체화한 근거다.
- AI 또는 파라미터 탐색이 라벨에 맞춰 변경돼도 별도 외부 표본 검증과 사용자 승격 승인을 거쳐야 한다(`PRM-003`).

## 7. 데이터팀 평가 데이터 계약

### 7.1 PostgreSQL 원천

평가 입력의 기준 원장은 PostgreSQL의 `daily_candle`과 `stock_master_snapshot`이다. 외부 API 응답을 평가 도중 즉석 혼합하지 않는다.

1. 요청한 `asOf` 이하에서 가장 최근의 `stock_master_snapshot.snapshot_date`를 선택한다.
2. 해당 스냅샷에 존재하는 종목만 평가 대상으로 인정한다.
3. `daily_candle.trade_date <= asOf` 조건을 SQL 조회 단계에서 강제한다.
4. 종목별 최대 거래일은 `asOf` 이하이어야 하며 실제 입력의 `dataAsOf`로 별도 기록한다.
5. 최신 품질 결과를 단순 적용하지 않고, 평가 입력과 연결 가능한 품질 스냅샷을 사용하도록 목표 계약을 둔다.

현재 DB에는 완전한 수집 동결 ID와 과거 시점 품질 연결이 없으므로, 초기 워크벤치는 아래의 논리적 동결 명세와 현재 한계를 반드시 표시해야 한다.

### 7.2 논리적 동결(`EvaluationSnapshot`)

평가를 시작할 때 다음 메타데이터를 불변 스냅샷으로 묶는다.

- 평가 ID와 생성 시각
- 요청 `asOf`, 실제 `dataAsOf`, 사용한 종목 스냅샷 날짜
- 종목 코드·이름·시장·상품 유형
- 입력 첫/마지막 거래일, 행 수
- 정렬된 각 일봉 핵심값을 이용한 입력 해시
- 품질 정책 버전·실행 ID·차단/경고 요약
- 후보 생성 알고리즘·파라미터·특징 사전 버전
- 애플리케이션 코드 버전 또는 커밋 식별자
- 데이터 상태: `READY`, `WARNING`, `BLOCKED`, `INSUFFICIENT`, `NOT_REPRODUCIBLE`

후보와 사용자 라벨은 모두 이 평가 ID를 참조한다. 이후 일봉이 수정되거나 품질 정책이 바뀌어도 기존 평가의 입력 해시와 결과는 바꾸지 않는다. 재평가는 새 평가 ID를 만든다.

### 7.3 미래 데이터 차단

다음은 완료 기준에 포함되는 필수 차단 규칙이다.

- SQL 단계에서 `trade_date > asOf` 행 제외
- 특징 계산기 입력 컬렉션에서도 최대 날짜를 재검사
- 회복·눌림 앵커, 변화점과 정규화 통계 모두 `asOf` 이하만 사용
- 차트 기본 표시도 `asOf`에서 끝나며 이후 가격을 사용자 평가 전에 노출하지 않음
- 사용자 라벨 저장 후 결과 확인 모드에서만 미래 구간을 별도 공개
- 백엔드 테스트에서 `asOf` 이후 극단값을 추가해도 후보와 특징이 동일함을 검증

차트가 미래 가격을 먼저 보여주면 사용자의 라벨 자체에 미래 정보가 섞이므로 API 계산뿐 아니라 UI 공개 순서도 데이터 누수 통제 범위에 포함한다.

### 7.4 데이터 부족과 품질 상태

| 상태 | 조건 | 처리 |
|---|---|---|
| `READY` | 통계 최소 표본과 필수 OHLCV가 있고 차단 문제가 없음 | 후보 생성·라벨 허용 |
| `WARNING` | 0 거래량, 소수 누락 등 허용 가능한 경고 | 후보 생성하되 경고와 영향 구간 표시 |
| `BLOCKED` | 잘못된 OHLC, 음수 거래량, 미확인 기업행사 등 차단 문제 | 자동 후보 생성 금지, 데이터 검토만 허용 |
| `INSUFFICIENT` | 최소 통계 표본 또는 급락 이전 탐색 이력 부족 | 가능한 범위를 표시하되 자동 적합 판정 금지 |
| `NOT_REPRODUCIBLE` | 종목 스냅샷·품질 실행·입력 해시 등 동결 근거 부족 | 연구 라벨로 사용 금지 |

최소 표본은 “박스권은 최소 N일”이라는 사업 규칙이 아니라 계산 신뢰도를 위한 기술 조건이다. 구간 후보별 표본 부족과 종목 전체 이력 부족을 구분한다.

### 7.5 평가 스냅샷 보존 계약

목표 저장 개념은 다음과 같다. 테이블명과 물리 스키마는 백엔드·DB 검토 후 별도 승인한다.

```text
evaluation_snapshot
 ├─ input metadata / hash / quality / versions
 ├─ evaluation_candidate (NARROW, EXPANDED, CONNECTED)
 │   └─ candidate_feature / gate / boundary evidence
 └─ user_evaluation_revision
     └─ selected candidate / edited boundary / labels / memo
```

- 원본 일봉 전체를 중복 복사할지, 일봉 PK 목록과 해시로 참조할지는 보존 비용과 사후 수정 정책을 함께 검토한다.
- 연구 재현을 최우선하면 입력 OHLCV를 별도 스냅샷으로 복사한다.
- 저장 비용을 줄이면 행 참조와 해시를 저장하되 `daily_candle`을 불변 원장으로 운영해야 한다.
- 어떤 방식을 택하든 평가 결과와 사용자 라벨의 삭제·덮어쓰기는 금지하고 리비전으로 관리한다.

## 8. 박스권 정의 차이 조율 절차

1. 전략연구팀이 후보별 정의와 특징 사전을 버전으로 제출한다.
2. 데이터팀이 실제 입력 범위·품질·재현 가능성을 검증한다.
3. 워크벤치는 세 후보를 동일 축과 동일 `asOf`로 표시한다.
4. 사용자는 선택·수정·거절하고 이유를 남긴다.
5. 전략팀은 유형별 선택률, 경계 수정 거리, 거절 사유를 집계한다.
6. 데이터팀은 선택 차이가 데이터 품질·이력 길이에서 비롯됐는지 분석한다.
7. 성과검증팀은 라벨을 보지 않은 외부 표본에서 후보 생성 안정성을 평가한다.
8. 의견이 갈리면 정의를 억지로 합치지 않고 좁은/확장/연결을 별도 전략 특징 또는 별도 버전으로 유지한다.
9. PM이 근거와 남은 선택지를 정리하고, 사용자가 최종 전략 정의와 자동 사용 범위를 승인한다.

사용자 라벨 다수결만으로 정의를 확정하지 않는다. 라벨 일관성, 데이터 품질, 이후 패턴 성과와 파라미터 민감도를 함께 본다.

## 9. 대안 비교

| 대안 | 장점 | 단점 | 검토 의견 |
|---|---|---|---|
| A. 현재 고정 창 유지 | 단순하고 기존 결과 재현 가능 | 사용자 정의와 불일치, 경계 설명이 약함 | 레거시 비교 기준으로만 유지 |
| B. 변화점 하나를 정답으로 사용 | 자동화가 간단하고 경계가 명확 | 알고리즘·페널티에 민감, 정의 차이를 숨김 | 초기 채택 반대 |
| C. 역방향 확장 하나만 사용 | 최신 패턴과 연결이 자연스러움 | 임계값 근처 불안정, 장기 구조를 놓칠 수 있음 | 후보 생성기 중 하나로 사용 |
| D. 복수 후보 워크벤치 | 사용자 정의를 자료화하고 알고리즘 차이를 비교 가능 | UI·저장·검토 비용 증가 | 본 제안의 권고안 |
| E. 전부 수동 라벨 | 사용자 의도 반영이 직접적 | 느리고 재현성이 낮으며 선택 편향이 큼 | 자동 후보가 실패한 보조 모드 |

## 10. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|

| 후보가 너무 많음 | 사용자 피로와 일관성 저하 | 유형별 대표 후보, 차이 요약, 보류 기능 제공 |
| 사용자 주관의 변화 | 라벨 불일치 | 라벨 리비전, 정의 가이드, 반복 표본으로 자기 일치도 확인 |
| 변화점 과민·둔감 | 경계 불안정 | 복수 파라미터 민감도와 역방향 확장 근거 병기 |
| 긴 구간이 짧은 구조 변화를 숨김 | 서로 다른 상태 병합 | 좁은 후보 보존, 변화점·이탈일 표시, 분리 라벨 |
| 데이터 누락을 안정 구간으로 오인 | 거짓 후보 | 품질 상태와 누락 구간 표시, 차단 시 자동 후보 금지 |
| 기존 일봉 수정으로 재현 실패 | 근거 상실 | 입력 해시·동결 메타데이터와 재평가 새 ID |
| 라벨에 과적합 | 실전 성과 붕괴 | 종목·시간 그룹 분리, 외부 표본과 워크포워드 검증 |

## 11. 미결정 사항

사용자 또는 후속 부서 조율이 필요한 항목이다.

1. 워크벤치 첫 평가 종목을 무작위·전략 후보·사용자 지정 중 어떤 비율로 구성할지
2. 유형별 대표 후보 최대 개수와 수동 라벨 목표 표본 수
3. 변화점 알고리즘 후보와 초기 파라미터 범위
4. 연결 후보에서 허용할 최대 단절과 실패 돌파 처리
5. 최소 통계 표본 수와 데이터 탐색 상한
6. 사용자 평가 전에 종목명과 이후 성과를 가릴지
7. 입력 일봉을 물리 복사할지 불변 원장 참조+해시로 보존할지
8. 경고 품질 종목을 라벨 데이터에 포함할지
9. 라벨을 최종 전략 점수에 직접 사용할지, 정의 연구에만 사용할지

## 12. 승인 후 완료 기준

아래 조건은 구현 작업의 완료 기준이며 현재 달성됐다는 뜻이 아니다.

- 실제 PostgreSQL 일봉으로 동일 평가 ID를 재조회했을 때 같은 후보·특징이 재현된다.
- `asOf` 이후 극단 가격을 추가해도 후보 경계와 모든 특징이 변하지 않는 자동 테스트가 통과한다.
- 좁은·확장·연결 후보가 생성 근거와 차이를 구조화해 제공한다.
- 각 후보에 자동 경계, 특징, 품질 상태, 알고리즘·파라미터 버전이 연결된다.
- 사용자가 선택·수정·거절·보류·수동 생성할 수 있고 원본 후보를 덮어쓰지 않는다.
- 평가 전에는 미래 차트가 노출되지 않으며 라벨 완료 후 별도 동작으로만 확인한다.
- `BLOCKED`, `INSUFFICIENT`, `NOT_REPRODUCIBLE` 상태는 자동 학습·전략 승인 자료에서 제외된다.
- 기존 v3 스캔과 백테스트 결과를 변경하지 않고 워크벤치 평가를 별도 저장한다.
- 전략·데이터·QA·성과검증 부서 검토 자료와 사용자 승인 기록이 평가 버전에 연결된다.
- 사용자 매뉴얼에 후보 유형, 라벨 의미, 미래 데이터 차단과 “매수 추천이 아님”이 설명된다.

## 13. 합동 권고

전략연구팀과 데이터팀은 **대안 D: 복수 후보 워크벤치**를 권고한다. 다만 1차 구현 범위는 자동매매 연결이 아니라 `실제 DB 일봉 동결 → 세 후보 비교 → 사용자 수정·라벨 보존 → 재현성 검증`으로 제한해야 한다. 이 단계에서 축적한 자료와 부서별 검토를 바탕으로 동적 안정 구간의 최종 정의를 별도 승인받는 것이 안전하다.
