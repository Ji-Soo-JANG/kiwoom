# STR-P06 사용자 박스권 평가 워크벤치 백엔드·UI 합동 검토서

- 문서 ID: `STR-P06-BEUI-01`
- 상태: 사용자 승인 대기 전 부서 검토안
- 작성 부서: 백엔드팀, 프론트엔드·UX팀
- 기준일: 2026-08-29
- 관련 요구사항: `STR-001~005`, `DAT-001~003`, `RES-001`, `NFR-002`, `NFR-005`, `NFR-006`, `NFR-008`
- 구현 여부: 이 문서는 계획·검토 자료이며 DB, API, 화면 구현을 포함하지 않는다.

## 1. 제안 목적

사용자가 실제 저장 일봉을 보면서 알고리즘이 제안한 박스권 후보를 비교하고, 경계를 직접 수정하며, 품질 라벨과 판단 근거를 남길 수 있는 연구용 워크벤치를 만든다. 사람이 확정한 평가는 동적 안정 구간 탐지기와 실제 사례·반례 데이터셋의 검증 근거로 사용한다.

가장 중요한 실험 원칙은 **평가 확정 전 미래 데이터의 완전한 비공개**다. 평가 기준일 이후의 일봉, 미래 수익률, 최고·최저가, 성공 여부, 결과를 암시하는 색상·정렬·문구를 API와 화면 모두에서 제공하지 않는다. 브라우저에 받아 숨기는 방식도 허용하지 않는다.

## 2. 평가 단위와 용어

| 용어 | 정의 |
|---|---|
| 평가 과제(batch) | 동일 데이터·알고리즘 버전과 표본 추출 정책으로 생성한 평가 묶음 |
| 평가 항목(item) | 한 종목의 한 기준일과 복수 박스권 후보를 평가하는 단위 |
| 관찰 종료일(cutoff) | 평가자가 볼 수 있는 마지막 거래일. 이후 자료는 미래 데이터다. |
| 후보(candidate) | 알고리즘 또는 기준 규칙이 제안한 박스권 시작·종료 구간 |
| 사용자 경계 | 평가자가 직접 선택하거나 수정한 박스권 시작·종료일 |
| 평가 확정(commit) | 라벨과 경계를 불변 스냅샷으로 제출하는 행위 |
| 결과 공개(reveal) | 평가 확정 후 별도 요청으로 cutoff 이후 평가 결과를 조회하는 행위 |

## 3. 사용자 흐름

```text
평가 과제 선택
→ 미평가 항목을 블라인드 순서로 열기
→ cutoff 이하 실제 일봉·거래량 확인
→ 복수 후보를 전환하거나 겹쳐 비교
→ 후보 채택 또는 차트에서 경계 직접 수정
→ 라벨·확신도·근거·문제 태그 입력
→ 평가 요약 확인
→ 평가 확정(이후 원본 수정 불가)
→ 사용자가 결과 공개 선택
→ 미래 성과와 사용자 판단 비교
```

평가 확정만으로 미래 결과가 자동 표시되지는 않는다. 확정과 공개를 분리해 사용자가 다음 항목을 블라인드 상태로 계속 평가할 수 있게 한다.

## 4. 백엔드 계획

### 4.1 보안 경계와 미래 데이터 비공개 원칙

1. 모든 평가용 일봉 SQL은 `trade_date <= cutoff_date`를 서버에서 강제한다.
2. 요청의 `from`, `to`, `limit` 값으로 cutoff를 넘어갈 수 없게 서버가 상한을 덮어쓴다.
3. 평가 조회 DTO에는 결과 요약, 미래 가격, 결과 존재 여부, 결과 ID를 포함하지 않는다.
4. 결과 공개 API는 평가가 `COMMITTED`이고 명시적인 reveal 요청이 저장된 경우에만 응답한다.
5. 일반 일봉 API는 평가 화면에서 호출하지 않는다. 워크벤치 전용 블라인드 API만 사용한다.
6. 후보 생성과 정렬은 cutoff 이하 자료만 사용하며 미래 성과로 후보 순서나 기본 선택을 바꾸지 않는다.
7. 서버 로그, 오류 메시지, ETag, 전체 개수, 캐시 키에도 미래 결과를 암시하는 값을 넣지 않는다.
8. 공개 전 응답은 서버에서 직렬화 검사를 거쳐 금지 필드가 없음을 계약 테스트로 보장한다.

개발자 도구에서 숨겨진 데이터가 보여서는 안 된다. CSS, 탭, 클라이언트 상태로 가리는 것은 블라인드가 아니다.

### 4.2 계획 데이터 모델

기존 `daily_candle`, `stock_master`, 전략 정의와 스캔 이력은 유지한다. 다음 테이블은 승인 후 별도 Flyway 버전으로 추가하는 안이다.

| `strategy_version_id` | 평가 대상 불변 전략 버전 |
| `dataset_version` | 데이터 동결·품질 정책 식별자 |
| `candidate_generator_version` | 후보 생성 코드·파라미터 버전 |
| `sampling_policy_json` | 종목·기준일 선택 정책 |
| `blind_policy_version` | 미래 비공개 정책 버전 |
| `status` | `DRAFT`, `READY`, `IN_PROGRESS`, `CLOSED`, `RETIRED` |
| `created_by`, `created_at` | 생성 감사 정보 |

#### `strategy_evaluation_item`

| 필드 | 의미 |
|---|---|
| `id`, `batch_id` | 항목과 과제 연결 |
| `code`, `cutoff_date` | 종목과 관찰 종료일 |

| `data_hash` | cutoff 이하 일봉 내용 해시 |
| `status` | `PENDING`, `DRAFTED`, `COMMITTED`, `REVEALED`, `VOID` |
| `committed_evaluation_id` | 확정 평가 연결 |
| `lock_version` | 동시 수정 방지 |

동일 과제의 `(code, cutoff_date)`는 유일해야 한다.

#### `strategy_evaluation_candidate`

| 필드 | 의미 |
|---|---|
| `id`, `item_id` | 후보 식별 |

| `generator_version` | 생성기 계약 버전 |

#### `strategy_evaluation_draft`

| 필드 | 의미 |
|---|---|
| `item_id`, `reviewer_id` | 사용자별 임시 저장 키 |
| `selected_candidate_key` | 선택 후보, 직접 구간이면 null 가능 |
| `edited_start_date`, `edited_end_date` | 사용자 경계 |
| `label_code`, `confidence` | 임시 라벨과 확신도 |
| `reason_codes`, `comment` | 구조화 근거와 메모 |
| `draft_revision`, `updated_at` | 낙관적 동시성·자동 저장 |

임시 저장은 덮어쓸 수 있으며 공식 연구 자료로 보지 않는다.

#### `strategy_evaluation`

| 필드 | 의미 |
|---|---|
| `id`, `item_id`, `reviewer_id` | 확정 평가 식별 |
| `selected_candidate_key` | 채택 후보 추적 |
| `final_start_date`, `final_end_date` | 최종 경계 |
| `label_code`, `confidence` | 확정 라벨과 확신도 |
| `reason_codes`, `comment` | 확정 근거 |
| `input_snapshot_json` | 제출 당시 모든 입력의 불변 사본 |
| `evaluation_schema_version` | 라벨·필드 계약 버전 |
| `committed_at` | 확정 시각 |

확정 레코드는 update/delete하지 않는다. 오류 정정은 원본을 보존한 `SUPERSEDED` 보정 평가를 별도 생성하는 정책을 후속 승인 대상으로 둔다.

#### `strategy_evaluation_reveal`

| 필드 | 의미 |
|---|---|
| `evaluation_id` | 확정 평가 연결 |
| `outcome_policy_version` | 미래 평가 창·성과 산식 버전 |
| `requested_by`, `revealed_at` | 공개 감사 정보 |
| `outcome_snapshot_json` | 공개 시점 결과의 불변 스냅샷 |

결과 스냅샷에는 예를 들어 미래 5·20·60거래일 수익률, 최대 유리·불리 변동, 목표/무효화 선도달 여부를 담을 수 있으나 구체 산식은 성과검증팀 승인이 필요하다.

### 4.3 API 계약안

| 메서드·경로 | 용도 | 미래 데이터 정책 |
|---|---|---|
| `GET /api/research/box-evaluations/batches` | 사용 가능한 과제와 진행률 | 성과·성공률 미포함 |
| `GET /api/research/box-evaluations/batches/{batchId}/next` | 다음 블라인드 항목 | 결과와 무관한 순서 |
| `GET /api/research/box-evaluations/items/{itemId}` | 종목 메타·후보·기존 draft | cutoff만 반환, reveal 필드 없음 |
| `GET /api/research/box-evaluations/items/{itemId}/candles` | 실제 OHLCV | 서버가 `date <= cutoff` 강제 |
| `PUT /api/research/box-evaluations/items/{itemId}/draft` | 자동·수동 임시 저장 | `If-Match` 또는 draft revision 필요 |
| `POST /api/research/box-evaluations/items/{itemId}/commit` | 평가 확정 | 멱등 키와 최종 확인 필요 |
| `POST /api/research/box-evaluations/items/{itemId}/reveal` | 미래 결과 공개 요청 | COMMITTED만 허용, 감사 기록 |
| `GET /api/research/box-evaluations/items/{itemId}/outcome` | 공개된 미래 결과 | reveal 존재 시에만 허용 |

평가 항목 응답 예시는 다음처럼 공개 전 자료만 포함한다.

```json
{
  "itemId": 42,
  "symbol": { "code": "005930", "name": "삼성전자", "market": "KOSPI" },
  "cutoffDate": "2024-06-28",
  "candlesAsOf": "2024-06-28",
  "candidates": [
    {
      "candidateKey": "C1",
      "startDate": "2023-01-10",
      "endDate": "2024-04-05",
      "features": { "rangeRate": 12.4, "volumeSpikeCount": 4 }
    }
  ],
  "draft": null,
  "evaluationSchemaVersion": "box-label-v1"
}
```

`futureAvailable`, `outcomeStatus`, 미래 일봉 수처럼 결과 존재를 암시하는 필드도 공개 전 응답에서 제외한다.

### 4.4 트랜잭션과 상태 전이

```text
PENDING ──draft──> DRAFTED ──commit──> COMMITTED ──reveal──> REVEALED
   │                   │
   └────── void ───────┴────────────> VOID
```

#### 임시 저장

- draft upsert와 revision 증가는 한 DB 트랜잭션으로 처리한다.
- 마지막으로 읽은 revision이 다르면 `409 CONFLICT`를 반환하고 서버·로컬 차이를 보여준다.
- 경계는 `첫 제공 일봉 <= start <= end <= cutoff`여야 한다.
- 임시 라벨은 미완성 상태를 허용한다.

#### 평가 확정

한 트랜잭션에서 다음을 수행한다.

1. 항목을 `SELECT ... FOR UPDATE`에 준하는 방식으로 잠근다.
2. 상태가 `PENDING/DRAFTED`인지, 멱등 키가 기존 확정과 같은지 확인한다.
3. 데이터 해시, cutoff, 후보 생성기와 평가 스키마 버전을 재검증한다.
4. 필수 라벨·경계·근거를 검증한다.
5. draft를 불변 `strategy_evaluation` 스냅샷으로 복사한다.
6. 항목을 `COMMITTED`로 변경하고 감사 이벤트를 기록한다.

확정 중 미래 결과를 계산하거나 조회하지 않는다.

#### 결과 공개

별도 트랜잭션에서 확정 상태와 권한을 확인하고 reveal 레코드를 유일하게 생성한다. 결과 스냅샷 계산은 `cutoff < trade_date <= outcome_end`만 사용한다. 동일 공개 요청은 같은 결과를 반환하며 산식 버전이 바뀌면 기존 스냅샷을 덮어쓰지 않는다.

### 4.5 버전 계약

각 확정 평가는 다음 버전을 반드시 연결한다.

- 데이터 동결·품질 정책 버전
- 후보 생성 전략·파라미터·코드 버전
- 블라인드 정책 버전
- 평가 라벨 스키마 버전
- 결과 산식 버전(공개 후)

`label_code`는 자유 문자열이 아닌 버전별 열거 계약으로 관리한다. v1 제안은 다음과 같다.

| 라벨 | 의미 |
|---|---|
| `VALID_BOX` | 의미 있는 안정 구간으로 판단 |
| `PARTIAL_BOX` | 일부는 맞지만 경계 또는 안정성이 불충분 |
| `NOT_BOX` | 박스권으로 보기 어려움 |
| `INSUFFICIENT_DATA` | 관찰 자료로 판단 불가 |
| `DATA_QUALITY_ISSUE` | 가격·거래량 자료 문제로 평가 제외 |

근거 코드는 `STABLE_RANGE`, `LOW_SLOPE`, `VOLATILITY_CONTRACTION`, `VOLUME_SPIKES`, `STRUCTURAL_BREAK`, `TRENDING`, `BOUNDARY_AMBIGUOUS`, `DATA_GAP` 등으로 시작할 수 있다. 라벨·근거 변경은 새 스키마 버전으로 만들고 이전 평가를 재해석하지 않는다.

## 5. 프론트엔드·UX 계획

### 5.1 화면 정보 구조

워크벤치는 일반 종목 차트와 분리된 연구 화면으로 제공한다.

```text

└─ 박스권 평가 워크벤치
   ├─ 진행 상태·블라인드 안내
   ├─ 실제 일봉/거래량 차트
   ├─ 복수 후보 전환·겹쳐 보기

   ├─ 라벨·확신도·근거 입력
   ├─ 임시 저장·평가 확정
   └─ 확정 후 선택형 미래 결과 공개
```

### 5.3 복수 후보 전환·비교

- 기본은 후보 한 개를 명확한 테두리와 패턴으로 표시한다.
- 후보 탭이나 라디오 버튼으로 즉시 전환하며 확대·축소와 스크롤 위치를 유지한다.
- “모두 겹쳐 보기”는 후보별 색상뿐 아니라 `C1`, `C2`, `C3` 선 패턴과 라벨을 함께 사용한다.
- 비교 표에는 cutoff 이하에서 계산한 기간, 강건 범위, 기울기, 변동성 축소, 거래량 급증만 보여준다.
- 알고리즘 순위는 표시할 수 있지만 “정답 가능성”처럼 보이지 않게 `제안 순서`라고 설명한다.
- 후보가 없을 때도 사용자가 차트에서 직접 구간을 만들 수 있다.

### 5.4 직접 구간 수정

- 차트 배경 드래그로 시작·종료를 선택하고 양쪽 손잡이로 경계를 조정한다.
- 날짜 입력 필드와 이전/다음 거래일 버튼을 함께 제공하여 정밀 수정과 키보드 조작을 지원한다.
- 경계는 실제 거래일로 스냅하며 휴장일 입력 시 가까운 거래일 선택을 사용자에게 알린다.
- 기존 후보를 수정하면 “C2에서 수정됨”, 새로 그리면 “직접 지정”으로 기록한다.
- 시작일이 종료일 이후거나 cutoff를 넘으면 즉시 오류를 설명하고 확정을 막는다.
- 원본 후보는 회색 점선으로 남겨 사용자 수정 폭을 비교할 수 있게 한다.

### 5.5 라벨 입력과 확정

- 라벨은 단일 선택, 근거는 복수 선택, 확신도는 1~5로 입력한다.
- `INSUFFICIENT_DATA` 또는 `DATA_QUALITY_ISSUE`는 구간 입력을 선택 사항으로 한다.
- 자유 메모는 보조 자료이며 구조화 라벨·근거를 대신하지 않는다.
- 임시 저장은 입력 중 자동 수행하고 상태와 마지막 저장 시각을 텍스트로 표시한다.
- 확정 전 요약 화면에서 종목, cutoff, 선택·수정 경계, 라벨, 근거를 다시 보여준다.
- 확정 버튼은 “평가 확정 — 이후 원본은 수정할 수 없음”으로 명시한다.

### 5.6 미래 결과 공개 화면

평가 확정 직후에는 다음 선택만 표시한다.

```text
평가가 확정되었습니다.
[다음 블라인드 평가로]   [미래 결과 공개]

미래 결과를 공개하면 이 항목의 cutoff 이후 가격과 성과를 보게 됩니다.
공개 여부와 시각은 연구 기록에 저장됩니다.
```

사용자가 공개를 선택한 뒤에만 다음을 요청하고 표시한다.

- cutoff를 경계로 한 과거·미래 영역 구분
- 미래 일봉과 사용자 구간의 연속 차트
- 사전에 승인된 5·20·60거래일 성과
- 최대 유리·불리 변동과 목표·무효화 선도달
- 사용자 라벨과 알고리즘 후보의 비교

성과의 상승·하락 색상은 공개 후에만 사용한다. 공개 전 진행률이나 후보 목록에는 미래 성과로 정렬된 정보가 없어야 한다.

### 5.7 접근성 기준

- 후보는 색상 외에 ID, 선 종류와 텍스트 범례로 구분한다.
- 모든 차트 조작은 키보드로 가능해야 하며 시작·종료 날짜 입력을 항상 제공한다.
- 차트에는 표 형식 데이터 요약과 선택 구간의 텍스트 설명을 제공한다.
- 드래그 손잡이는 충분한 클릭 영역과 보이는 포커스 표시를 갖는다.
- 자동 저장, 충돌, 확정, 공개 상태는 `aria-live`로 알리되 반복적으로 읽지 않는다.
- 오류는 해당 입력과 연결하고 해결 방법을 문장으로 제공한다.
- 확정·공개 대화상자는 포커스를 가두고 ESC 취소, 명확한 제목과 결과 설명을 제공한다.
- 모바일을 우선 지원하지 않더라도 200% 확대에서 입력과 버튼이 겹치지 않아야 한다.

## 6. 검토 대안

### 대안 A: 서버 강제 블라인드 워크벤치(권고)

- cutoff 이하 전용 API와 별도 reveal API를 사용한다.
- 확정 평가와 공개 기록을 불변 저장한다.
- 장점: 미래 누수 방지, 감사·재현성, 다부서 연구 활용에 가장 안전하다.
- 단점: 별도 스키마·API·상태 전이가 필요해 구현량이 크다.

### 대안 B: 기존 일봉 API를 프론트에서 잘라 표시

- 전체 일봉을 받아 cutoff 이후를 화면에서 숨긴다.
- 장점: 구현이 빠르다.
- 단점: 네트워크·개발자 도구·클라이언트 캐시에 미래 데이터가 노출되어 `RES-001`을 위반한다.
- 판정: 채택 불가.

### 대안 C: 결과를 전혀 공개하지 않고 일괄 평가 종료 후 보고서만 제공

- 개별 평가 중 결과 공개 기능을 제공하지 않는다.
- 장점: 학습 효과와 평가자 편향을 가장 강하게 차단한다.
- 단점: 사용자의 즉각적인 사례 학습과 오류 발견이 어렵다.
- 판정: 엄격 연구 모드 옵션으로는 유효하다. 과제별 `reveal_policy=AFTER_ITEM|AFTER_BATCH|NEVER`를 두는 절충안을 권고한다.

## 9. 사용자 승인 필요 결정

1. 서버 강제 블라인드인 대안 A를 기본 구조로 채택할지
2. 결과 공개 정책을 `항목 확정 후 선택 공개`, `과제 전체 완료 후 공개`, `비공개` 중 과제별 선택하게 할지
3. v1 평가 라벨을 `유효/부분 유효/무효/자료 부족/품질 문제`로 시작할지
4. 사용자가 알고리즘 후보를 수정하는 것뿐 아니라 완전히 새 구간도 그릴 수 있게 할지
5. 확정 오류 정정을 원본 보존형 supersede 평가로 허용할지
6. 평가 중 종목 코드·이름을 보여줄지, 완전 블라인드 모드를 추가할지

## 10. 완료 기준

승인 후 구현의 완료는 다음 조건을 모두 만족할 때로 제안한다.

### 백엔드

- 공개 전 모든 평가 API가 cutoff 이후 일봉·파생값·결과 존재 힌트를 반환하지 않는다.
- URL 파라미터 조작과 일반 일봉 API 우회로 평가 세션의 미래 데이터를 획득할 수 없다.
- 평가 과제, 데이터, 생성기, 블라인드, 라벨과 결과 산식 버전을 역추적할 수 있다.
- 임시 저장 충돌을 감지하고 확정 요청은 멱등하다.
- 확정 평가는 불변이며 공개는 별도 감사 이벤트로 남는다.
- 경계와 후보의 모든 날짜가 실제 제공 범위와 cutoff 안에 있음을 서버가 검증한다.

### 프론트엔드·UX

- 실제 OHLCV 차트에서 최소 3개 후보를 전환·겹쳐 비교할 수 있다.
- 마우스와 키보드 모두로 경계를 만들고 수정할 수 있다.
- 구조화 라벨, 확신도, 근거와 메모를 임시 저장하고 확정할 수 있다.
- 확정 전 UI·네트워크·클라이언트 캐시에 미래 데이터가 존재하지 않는다.
- 확정 후에도 사용자가 명시적으로 공개하기 전 미래 결과를 요청하지 않는다.
- 후보, 경계, 저장·충돌·확정·공개 상태가 색상 없이도 이해 가능하다.

### 검증

- cutoff를 하루 넘기는 요청, 큰 limit, 직접 URL, 캐시 복원, 재로그인 우회 시험이 모두 차단된다.
- 후보 순서와 공개 전 응답이 미래 일봉을 추가해도 변하지 않는 속성 테스트를 통과한다.
- 두 탭 동시 편집, 중복 확정, 네트워크 재시도, 공개 재요청이 데이터 중복 없이 수렴한다.
- 접근성 자동 검사와 키보드 전용 핵심 여정 E2E를 통과한다.
