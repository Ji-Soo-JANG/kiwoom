# STR-P06 사용자 박스권 평가 워크벤치 — PM 승인 제안서

- 문서 ID: `STR-P06-PM-01`
- 기준일: 2026-08-29
- 상태: **사용자 승인 대기**
- PM 결론: 조건부 구현 승인 권고
- 구현 상태: 미구현

## 1. 승인 요청 요약

실제 PostgreSQL 일봉을 기준일 당시 상태로만 보여주고, 서로 다른 박스권 후보를 한 차트에서 비교·수정·평가하는 연구용 GUI를 제안한다. 사용자가 생각하는 박스권을 단일 수식으로 미리 고정하지 않고 실제 사례에 대한 선택과 수정 근거를 자료화하는 것이 목적이다.

이번 승인은 **연구 평가 도구 구현**에 한정한다. 자동매매, PAPER/LIVE 주문, 전략 자동 승격, 자금 배분에는 연결하지 않는다.

PM은 다음 조건으로 승인을 권고한다.

1. 후보는 역방향 확장과 변화점 탐지를 혼합해 `NARROW`, `EXPANDED`, `CONNECTED`를 제시한다.
2. 평가 확정 전에는 기준일 이후 데이터를 서버가 반환하지 않는다.
3. 사용자는 후보 선택뿐 아니라 경계 수정, 직접 구간 생성, 거절·보류가 가능하다.
4. 자동 후보와 확정 평가는 덮어쓰지 않고 수정 이력을 새 리비전으로 보존한다.
5. 미래 성과는 평가 확정 후 별도 공개 동작으로만 조회한다.
6. 연구 서비스와 주문·자동매매 경로를 코드, API, 권한과 테스트에서 분리한다.

## 2. 배경과 의사결정 이유

현재 전략은 고정된 여러 기간 창에서 점수가 높은 구간을 선택한다. 그러나 사용자가 말하는 박스권은 수개월 또는 수년일 수 있고 기간 자체보다 가격 상태의 안정성, 간헐적 거래량 급증, 급락·회복·눌림의 현재 진행 순서가 중요하다.

동적 알고리즘 하나를 바로 정답으로 채택하면 사용자 정의와 알고리즘 정의의 차이를 감춘다. 반대로 모든 경계를 수동으로 그리면 느리고 일관성과 재현성이 낮다. 따라서 알고리즘이 서로 다른 성격의 후보를 제시하고, 사용자가 실제 데이터로 비교·교정하는 방식이 가장 적합하다.

## 3. 승인 범위

### 포함

- PostgreSQL `daily_candle`과 시점 기준 종목 스냅샷을 사용하는 평가 과제
- `asOf/cutoff` 이하 일봉만 사용하는 불변 입력 스냅샷과 해시
- 역방향 확장 + 변화점 탐지 기반 복수 후보 생성
- 좁은·확장·연결 후보의 경계, 특징, 차이와 품질 상태 표시
- 실제 OHLCV·거래량 차트의 후보 전환 및 겹쳐 보기
- 마우스와 키보드에 의한 경계 수정 및 사용자 신규 구간 생성
- 구조화 라벨, 확신도, 사유, 메모의 임시 저장과 확정
- 확정 평가 잠금, 원본 보존형 정정, 감사·버전 이력
- 평가 확정 후 명시적 미래 결과 공개와 별도 결과 스냅샷
- 미래 누수, 동시 수정, 재현성, 접근성, 주문 분리 자동 테스트

### 제외

- 사용자 라벨을 이용한 AI 학습 또는 운영 전략 자동 변경
- 전략의 PAPER/LIVE 자동 승격과 주문 후보 생성
- 자동매매 ON/OFF, 주문, 포지션, 위험 한도 조작
- 자금 규모별 배분과 미래 유망 후보를 위한 현금 예약
- 보유 종목 강제 교체와 최대 보유 종목 수 결정
- 외부 뉴스·기업행사·과거 유니버스 신규 연동
- 전략 수익성 또는 실전 사용 가능성의 확정

미래 후보의 기대 이익이 더 크면 현금을 남기는 원칙은 별도 `CAP-P01 자금 예약·기회비용 모델` 안건으로 다룬다. STR-P06은 그 모델에 필요한 신뢰 가능한 패턴 자료를 제공할 뿐 자금을 움직이지 않는다.

## 4. 사용자 평가 흐름

```text
평가 과제 선택
→ 서버가 cutoff 이하 입력을 동결하고 해시 검증
→ 좁은/확장/연결 후보 생성
→ 실제 일봉 차트에서 후보 전환·겹쳐 비교
→ 후보 선택, 경계 수정 또는 직접 구간 지정
→ 라벨·확신도·근거·메모 임시 저장
→ 사용자 확인 후 평가 확정·잠금
→ 다음 블라인드 평가 또는 명시적 미래 결과 공개
→ 결과와 판단 차이를 별도 연구 자료로 보존
```

평가 확정 직후 미래 자료를 자동 요청하지 않는다. 사용자는 다음 블라인드 평가를 계속하거나 결과 공개를 선택할 수 있다. 과제별로 `항목 확정 후`, `과제 완료 후`, `공개하지 않음` 정책을 둘 수 있도록 설계한다.

## 5. 후보와 라벨 v1

### 후보 유형

| 후보 | 의미 | 주의점 |
|---|---|---|
| `NARROW` | 최근 상태를 엄격히 만족하는 핵심 구간 | 장기 축적을 짧게 볼 수 있음 |
| `EXPANDED` | 유사한 가격·변동성 상태를 과거 방향으로 확장 | 다른 상태를 합칠 수 있음 |
| `CONNECTED` | 짧은 이탈을 사이에 둔 유사 안정 구간 연결 | 사후 편의적 연결 위험이 큼 |
| `USER_ADDED` | 자동 후보 없이 사용자가 직접 지정 | 탐지기 성공으로 집계하지 않음 |

박스권 기간은 특징으로 기록하지만 사업상 최소·최대 일수로 자격을 고정하지 않는다. 통계 계산에 필요한 최소 표본만 기술 조건으로 관리한다.

### 평가 입력

- 적합성: `VALID_BOX`, `PARTIAL_BOX`, `NOT_BOX`, `INSUFFICIENT_DATA`, `DATA_QUALITY_ISSUE`
- 후보 관계: 원본 유지, 경계 수정, 사용자 직접 생성, 분리 필요, 연결 필요
- 확신도: 1~5
- 구조화 사유: 안정 범위, 낮은 기울기, 변동성 축소, 거래량 급증, 구조 단절, 추세 구간, 경계 모호, 데이터 공백 등
- 자유 메모: 구조화 입력의 보조 자료

사용자가 생각하는 박스권 정의는 선택률만으로 확정하지 않는다. 경계 수정 거리, 거절 사유, 자기 일치도, 데이터 품질과 이후 성과를 함께 검토한다.

## 6. 기술 경계

### 데이터 개념

승인 후 물리 스키마는 별도 설계 검토를 거치되 다음 개념을 유지한다.

- `strategy_evaluation_batch`: 표본·데이터·생성기·블라인드 정책이 고정된 평가 과제
- `strategy_evaluation_item`: 종목, cutoff, 입력 해시와 상태를 가진 평가 항목
- `strategy_evaluation_candidate`: 자동 후보 경계와 cutoff 이하 특징
- `strategy_evaluation_draft`: 수정 가능한 사용자별 임시 저장
- `strategy_evaluation`: 확정 후 변경할 수 없는 평가 스냅샷
- `strategy_evaluation_reveal`: 결과 공개 요청과 성과 산식 버전

입력 일봉 전체 복사와 불변 원장 참조+해시 방식은 저장량과 재현성 검증 후 상세설계에서 확정한다. 어떤 방식을 택해도 기존 평가를 덮어쓰지는 않는다.

### API 경계

연구 기능은 `/api/research/box-evaluations/**` 전용 API로 분리한다. 평가 조회·일봉 응답은 cutoff 이후 가격, 파생값, 결과 존재 여부를 포함하지 않는다. 확정과 결과 공개는 서로 다른 요청과 트랜잭션으로 처리한다.

일반 차트 API에서 전체 일봉을 받아 브라우저가 숨기는 방식은 채택하지 않는다. 평가 화면은 전용 블라인드 API만 사용한다.

### 상태와 불변성

```text
PENDING → DRAFTED → COMMITTED → REVEALED
    └──────────────→ VOID
```

- draft는 revision을 사용해 두 탭의 동시 수정을 감지한다.
- commit은 멱등 키, 입력 해시와 정책 버전을 재검증한다.
- 확정 평가의 update/delete는 허용하지 않는다.
- 오류 정정은 원본을 참조하는 새 평가로 남긴다.
- reveal은 확정 평가에서만 가능하고 감사 시각과 결과 산식을 보존한다.

## 7. 편향·위험 통제

| 위험 | 필수 통제 |
|---|---|
| 미래 정보가 라벨에 섞임 | SQL·서비스·DTO·UI 모두 cutoff 강제, 브라우저에 미래 자료 미전송 |
| 성공 사례만 선택 | 사용자 사례와 무작위/전수·반례·무신호·봉인 세트 분리 |
| 후보 순위가 정답처럼 작용 | 미래와 무관한 결정론적 정렬, 동일 축 비교, `해당 없음` 허용 |
| 사용자 경계의 사후 편향 | 원 후보와 수정본·이유 보존, `USER_ADDED` 별도 집계 |
| 평가 후 기준 변경 | 계획·지표·표본 잠금, 변경 시 부모를 가진 새 버전 생성 |
| 골든 세트 과적합 | 연구/조정, 회귀 골든, 봉인 최종 평가 세트 분리 |
| 연구 결과의 주문 오용 | 연구 서비스·DB 권한·API와 주문 경로 분리, 주문 0회 통합 테스트 |
| 단일 사용자 주관 | 확신도·반복/독립 라벨·불일치 보존, 절대 정답으로 사용 금지 |

현재 단계에서 기업행사 외부 데이터를 새로 연동하지 않는 사용자 원칙을 유지한다. 다만 데이터상 의심되는 급격한 불연속은 `품질 문제/검토 필요`로 표시하고 자동 연결하지 않는다.

## 8. 구현 단계와 단계별 중단점

사용자 승인 후에도 한 번에 주문 기능까지 확장하지 않는다.

### 1단계 — 계약과 데이터 기반

- 평가·라벨·블라인드·버전 계약 확정
- 데이터 모델과 마이그레이션
- cutoff 전용 조회, 후보 생성, draft/commit/reveal API
- 미래 누수 및 불변성 계약 테스트

완료 시 백엔드·데이터·QA 부서가 증적을 검토한다.

### 2단계 — 평가 GUI

- 과제 목록과 블라인드 진행 화면
- 실제 일봉·거래량 차트, 후보 전환·겹쳐 보기
- 경계 수정, 직접 구간, 라벨·확신도·근거 입력
- 자동 저장, 충돌 해결, 확정과 선택 공개
- 키보드 조작과 200% 확대 접근성

완료 시 전략·UX·QA 부서가 실제 사례로 검토한다.

### 3단계 — 검증 자료화

- 사용자·반례·무작위/전수·골든·봉인 세트 분리
- 결과 산식 버전과 후속 성과 공개
- 경계 일치도, 라벨 일치도, 후보별 탐지·성과 비교 보고서
- 주문·자동매매 상태 불변 통합 시험

완료 후 PM이 결과를 종합하고, 동적 박스권 정의 또는 후속 전략 연구는 사용자에게 다시 승인받는다.

## 9. 이번 승인에서 확정하지 않는 연구값

다음 값은 수익 결과를 보기 전에 별도 평가 계획으로 버전·잠금해야 하지만, 현재 제안 승인 시 임의 숫자로 고정하지 않는다.

- 후보 유형별 최대 표시 개수
- 평가 표본 수와 시장 국면별 할당
- 변화점 알고리즘과 초기 파라미터 범위
- 연결 후보의 최대 단절 허용치
- 통계 계산 최소 표본과 데이터 탐색 상한
- 후속 성과의 거래일 지평과 성공·무효화 정의
- 공식 주 지표, 비용·슬리피지·체결 가능성 가정
- 라벨 독립 검토 방식과 골든 편입 일치 기준

이 값들은 구현 전에 기본값 제안과 근거를 문서화하고, 같은 평가 버전 안에서 결과를 본 뒤 바꾸지 못하게 한다.

## 10. 완료 및 승인 차단 기준

### 완료 기준

- 같은 입력 해시·정책·코드 버전에서 후보와 특징이 재현된다.
- cutoff 이후 극단 일봉을 추가해도 공개 전 후보와 응답이 변하지 않는다.
- 복수 후보의 원본과 사용자 수정본이 함께 보존된다.
- 확정 전 UI·네트워크·캐시에 미래 데이터가 없다.
- 확정 평가는 잠기며 정정과 공개가 별도 감사 기록으로 남는다.
- 사용자 사례뿐 아니라 반례·무신호·무작위/전수·봉인 표본을 분리한다.
- 부서 검토서의 `P06-QA-001~031`이 통과한다.
- 연구 실행 전후 주문·후보·포지션·자동매매 상태가 변하지 않는다.

### 승인 차단

미래 데이터 서버 차단, 확정 평가 원본 보존, 표본 편향 통제, 주문 경로 분리 중 하나라도 빠지는 설계 변경은 PM이 구현하지 않고 사용자에게 다시 보고한다.

| 백엔드·UI | 대안 A 권고 | 서버 강제 블라인드, 확정/공개 분리, 접근 가능한 경계 편집 |
| QA·성과검증·위험 | 조건부 승인 권고 | 평가 계획 잠금, 다양한 표본군, 주문과 완전 분리 |
| PM | 조건부 구현 승인 권고 | 위 공통 조건을 필수 범위로 유지하고 미결정 연구값을 사전 등록 |

부서 간 본질적인 반대는 없다. 라벨 명칭과 평가 상태 명칭은 문서마다 차이가 있어 구현 계약에서는 본 제안서의 사용자용 라벨과 상태를 기준으로 통합하고, 내부 연구 세트의 `POSITIVE/NEGATIVE/AMBIGUOUS/DATA_INVALID` 매핑은 상세설계에서 명시한다.

## 12. 사용자 승인 요청

승인 대상은 아래 한 문장이다.

> **STR-P06을 본 제안서의 포함·제외 범위와 차단 조건대로 1~3단계 구현하고, 각 단계의 부서 검토 자료를 남긴다. 전략 승격·자금 배분·주문 연결은 별도 제안과 사용자 승인 없이는 진행하지 않는다.**

사용자가 `승인`하면 상태를 승인으로 변경하고 1단계 상세 구현 계획부터 진행한다. 수정 조건이 있으면 그 조건을 제안서와 승인 기록에 먼저 반영한 뒤 다시 승인 상태를 확인한다.
