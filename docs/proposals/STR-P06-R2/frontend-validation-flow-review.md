# STR-P06-R2 UI·검증 흐름 검토 및 최소 변경안

- 문서 ID: `STR-P06-R2-FE-REVIEW-02`
- 기준일: 2026-08-30
- 상태: 현재 계약 기준 검토 완료
- 범위: 박스권 단독 분류·경계 탐지 검증. 수익성·주문·전체 전략은 제외한다.

## 1. 검토 결론

별도의 정의 확인 화면을 기다리지 않고도 현재 batch/item/candidate/draft/commit 계약으로 신규 탐지기 검증 배치를 평가할 수 있다. 최소 사용자 흐름은 `배치 선택 → 다음 블라인드 → 후보 비교·경계 수정 → 라벨·확신도·근거 입력 → 확정 → 다음 항목 자동 전환 → 배치 완료`다.

현재 성과 공개 버튼과 미래 성과 표는 R2 검증 질문에 포함되지 않고 후속 판단을 편향시킬 수 있으므로 워크벤치에서 제거한다. 백엔드 reveal/outcome 저장 기반을 즉시 삭제할 필요는 없지만 R2 화면과 검증 집계에서는 호출하지 않고 격리한다.

## 2. 독립적으로 적용한 프론트 변경

- 화면 제목과 안내를 `박스권 경계 탐지 검증` 및 `BASE_ONLY` 의미로 변경
- 종목 코드를 화면에서 숨기고 `블라인드 평가 항목`으로 표시
- 알고리즘 후보 키를 `후보 1`, `후보 2`처럼 익명 표시
- 미래 결과 공개 버튼·성과 표·호출 상태 제거
- 확신도 기본값 3을 제거하고 1~5를 의도적으로 선택하도록 변경
- `PARTIAL_BOX`, `INSUFFICIENT_DATA`는 설명 입력을 필수화
- 라벨·확신도·근거·조건부 설명이 충족될 때만 확정 가능
- 확정 성공 후 다음 미완료 항목 자동 전환과 상태 초기화 유지

내부 `candidateKey`와 `item.code`는 현재 API 호환을 위해 그대로 사용한다. 화면에서 숨겼다는 사실만으로 완전한 서버 블라인드가 되지는 않는다.

## 3. 백엔드에 필요한 최소 계약 변경

탐지기 알고리즘 DTO를 프론트가 추정하지 않도록 아래 계약만 안정화해야 한다.

1. 배치에 `evaluationScope=BASE_ONLY`, `detectorVersion`, `datasetVersion`, `blindPolicyVersion`을 명시한다.
2. 평가 item 응답에서 실제 종목 코드 대신 배치 내 불변 `blindAlias`를 제공한다. 실제 코드는 서버에만 보관한다.
3. 후보 응답은 안정된 opaque `candidateKey`, 시작·종료일만 필수로 한다. 점수, 예상 라벨, 알고리즘 종류는 확정 전 응답에서 제외한다.
4. `/next`는 남은 항목이 없으면 `204 No Content`를 반환한다.
5. 배치 완료 전에는 분류 성능, IoU, 후보 수정률과 숨은 반복 매핑 API를 공개하지 않는다.
6. 검증 배치 생성 시 탐지기와 파라미터를 동결하고 기존 평가 원본을 덮어쓰지 않는다.
7. reveal/outcome API는 R2 권한·라우트에서 차단하거나 별도 legacy research scope로 격리한다.

권고 최소 item 계약:

```json
{
  "item": {
    "id": 10,
    "blindAlias": "항목 018",
    "cutoffDate": "2025-04-30",
    "evaluationScope": "BASE_ONLY"
  },
  "candidates": [
    { "candidateKey": "opaque-key", "startDate": "2023-01-02", "endDate": "2025-03-31" }
  ],
  "draft": null,
  "evaluationSchemaVersion": "box-label-v2"
}
```

프론트는 위 신규 필드가 확정되기 전까지 현재 응답 필드를 더 추정하거나 탐지기 특징값을 화면에 연결하지 않는다.

## 4. 신규 검증 배치 사용자 흐름

1. 운영자가 탐지기·데이터·표본 정책이 동결된 R2 배치를 생성한다.
2. 사용자는 과제 목록에서 R2 배치를 고르고 첫 블라인드 항목을 연다.
3. 화면은 cutoff 이하 실제 일봉과 익명 후보 경계만 표시한다.
4. 사용자는 후보를 비교하고 한 후보를 채택하거나 경계를 직접 수정한다.
5. `VALID`, `PARTIAL`, `NOT_BOX`, `INSUFFICIENT_DATA`, `DATA_QUALITY_ISSUE` 중 하나를 선택한다.
6. 확신도와 최소 한 개 근거를 선택한다. 부분 유효·자료 부족은 설명도 입력한다.
7. 확정 성공 시 같은 배치의 다음 항목이 자동 표시된다. 실패하면 현재 입력과 항목을 유지한다.
8. 마지막 항목 확정 후 완료 안내만 표시하고 누적 지표는 아직 공개하지 않는다.
9. 배치가 서버에서 종료되고 숨은 반복을 포함한 모든 평가가 확정된 뒤 별도 검증 보고서에서 분류·경계·일관성 지표를 공개한다.

## 5. 기존 성과 기능 격리안

| 요소 | R2 처리 | 후속 처리 |
|---|---|---|
| 워크벤치 미래 결과 버튼 | 제거 | 수익성 연구 전용 별도 화면에서만 검토 |
| 미래 5·10·20일 성과 표 | 제거 | 전체 패턴·진입 연구 승인 후 사용 |
| `revealBoxEvaluationOutcome` 프론트 API | 현재 호환을 위해 잔존 가능, R2에서 미사용 | 호출자 0건 확인 후 별도 제거 승인 |
| 백엔드 reveal/outcome API·테이블 | R2에서 격리 | 기존 파일럿 감사 이력 보존 때문에 즉시 삭제 금지 |
| 파일럿 성과 문서 | 역사 자료로 보존 | R2 탐지 통과 근거로 인용 금지 |

## 6. 테스트 계획

### 프론트 단위·통합

- 종목 코드와 내부 후보 키가 화면에 노출되지 않는다.
- 미래 결과 공개 버튼과 성과 표가 존재하지 않고 reveal API를 호출하지 않는다.
- 확신도 미선택 상태에서는 확정할 수 없다.
- 라벨·확신도·근거 최소 조건을 검사한다.
- `PARTIAL_BOX`, `INSUFFICIENT_DATA`는 설명 없이는 확정할 수 없다.
- 확정 성공 시 다음 항목으로 전환하고 이전 draft/message/후보 상태를 초기화한다.
- 확정 실패 시 현재 항목과 입력을 유지한다.
- 마지막 항목의 204/빈 응답은 완료 상태로 표시한다.

### 백엔드 계약·보안

- item/candidate/candle 응답에 cutoff 이후 일봉·성과·예상 라벨·점수가 없다.
- blind item 응답에 실제 code/name과 숨은 반복 그룹이 없다.
- cutoff 이후 극단값을 추가해도 공개 전 후보와 특징이 동일하다.
- 배치 완료 전 검증 집계와 반복 매핑 조회가 거부된다.
- 연구 패키지에서 주문·브로커·자동매매 의존이 없다.

### E2E

- R2 배치 선택부터 마지막 항목 완료까지 키보드만으로 수행한다.
- 네트워크 실패 후 입력이 보존되고 재시도로 한 번만 확정된다.
- 두 탭 draft 충돌과 오래된 revision을 명확히 안내한다.
- 200% 확대, 색상 제거와 스크린리더 상태 안내를 확인한다.

## 7. 남은 위험

- 현재 API는 실제 `code`와 의미 있는 `candidateKey`를 브라우저에 보내므로 화면 익명화만으로는 완전한 블라인드가 아니다.
- 후보 경계 직접 드래그는 아직 없고 날짜 입력만 제공한다. 장기 차트 평가 효율을 위해 후속 UI 구현이 필요하다.
- 배치 진행률·완료 상태 계약이 없어 목록에서 정확한 잔여량을 표시하지 못한다.
- 숨은 반복과 배치 완료 후 분류·경계 집계 계약은 아직 프론트가 사용할 수 없다.
- reveal API가 남아 있으므로 R2 권한 분리가 없으면 사용자가 직접 호출할 가능성이 있다.

## 8. 완료 판단

이번 최소 프론트 변경은 R2 평가 입력 흐름을 제공하지만, 완전한 독립 검증 완료로 보지 않는다. 서버 blind alias, 점수·알고리즘 정보 비공개, 배치 종료 후에만 집계 공개, 탐지기·데이터 버전 동결이 백엔드와 QA에서 확인돼야 R2 검증 실행 준비가 완료된다.
